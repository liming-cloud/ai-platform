## 设计定位

AI Platform 前端不是营销页、产品官网或演示大屏，而是企业管理员和租户管理员反复使用的运营控制台。设计目标是高密度、可扫描、状态明确、权限边界清晰，并能支撑平台管理、租户配置、模型调用、知识库、工具治理和观测页面逐步扩展。

现有 S3/S4 控制台已满足真实登录、RBAC 菜单、Provider Catalog、IAM 管理和页面 smoke，但视觉系统仍偏最小可用纵切。后续所有前端工作必须先满足本设计系统，再追加业务页面。

## A2 视觉基准

当前前端视觉方向由产品工程师、UI 工程师和资深前端工程师共同收敛为 `A2: OpenAI 式克制 + macOS 式桌面质感`。

概念图事实源：`docs/assets/frontend-design/a2-openai-macos-console-concept.png`。

角色结论：

- 产品工程师：控制台首屏必须服务真实模型配置、Provider inventory、租户上下文、权限和状态反馈；不得用营销式 hero 或假指标掩盖业务操作。
- UI 工程师：采用安静、现代、精致的 SaaS 控制台质感，参考 OpenAI 的低噪声和 macOS 的 sidebar / toolbar / grouped panels，但不得复制 OpenAI 或 Apple 品牌资产。
- 资深前端工程师：落地时必须拆出可复用应用壳、导航、toolbar、summary、form、table、provider inventory、status badge 和 message 规则，避免继续扩大单文件临时页面。

A2 设计特征：

- 轻量 macOS 式桌面结构：左侧 sidebar、顶部 toolbar、租户上下文胶囊、用户区和分组内容区。
- OpenAI 式低噪声：白色和冷中性浅灰为主，少量 teal 作为品牌动作色，不使用大面积渐变、装饰光斑或暗色大屏。
- 企业控制台密度：表单、表格和 provider inventory 在首屏内可扫描，主操作明确，readonly、success、error、disabled 状态稳定。
- 组件半径和边界：面板、输入、按钮默认 6px 到 8px 圆角，使用 1px 分割线和轻微阴影，不做卡中卡和胶囊堆砌。

## 主流平台与自适应验收基准

用户复核后明确：前端不能只做到“接近概念图”，必须由产品工程师、UI 工程师和资深前端工程师共同把控实际验收，并吸收当前主流 SaaS / 控制台平台的稳定审美。后续实现以 `A2+` 为准：保留 OpenAI 式低噪声和 macOS 式工作台结构，同时借鉴 Vercel / Linear / Stripe / Ant Design 一类主流平台的克制边界、紧凑密度、清晰 toolbar、稳定 sidebar、可扫描表格和跨分辨率布局纪律。

三角色验收职责：

| 角色 | 验收重点 | 不通过示例 |
| --- | --- | --- |
| 产品工程师 | 首屏是否服务真实任务；菜单、租户上下文、配置表单、供应商清单、错误/成功反馈是否可直接验收 | 首屏被装饰、导航或说明文案占据；真实主任务需要滚动多屏才可见 |
| UI 工程师 | 视觉是否现代、克制、统一；token、间距、边界、圆角、状态徽标、表格密度是否像企业控制台 | 同一页面出现多套半径/阴影/边框；按钮、徽标、卡片风格不统一 |
| 资深前端工程师 | 版式是否使用稳定断点、最大宽、gutter、滚动容器和可复用 primitives；不同分辨率是否无漂移 | 1440、1280、1024、390 宽度下内容宽度突变、横向溢出、按钮裁切或移动端被纵向导航吞掉 |

分辨率验收矩阵：

| 视口 | 产品验收 | UI 验收 | 前端验收 |
| --- | --- | --- | --- |
| 1440px 桌面 | 模型配置表单和供应商清单同屏可见，租户/用户/状态在 toolbar 清晰 | 内容最大宽居中，sidebar 与工作区比例稳定 | 页面 `scrollWidth` 不大于视口宽度，provider table 仅在自身容器内横向滚动 |
| 1280px 笔记本 | 主任务仍可扫描，表单和清单可以一列或两列重排 | 间距不塌陷，卡片高度和状态徽标稳定 | 触发明确断点，不出现半截列或隐藏按钮 |
| 1024px 平板/窄屏 | 主操作、租户上下文和当前菜单仍在首屏可理解 | toolbar 可换行但不失控，表格有滚动容器 | 内容区使用单列时保持统一 gutter |
| 390px 移动 | 首屏不能被完整纵向菜单占满；应优先看到当前页面标题和状态 | 导航变为紧凑横向滚动，按钮不裁切 | 无全页面横向溢出；表格横向滚动限定在 `.table-scroll` |

## A2+ 管理页面完成态

用户复核后进一步明确：企业级控制台不能只停留在“表单可用”，平台管理类页面必须采用管理后台的稳定产品模型。产品工程师、UI 工程师和资深前端工程师共同验收以下标准：

- 管理对象默认入口必须是分页列表，包含总数、当前页、空状态、错误状态、状态字段和最右侧 `操作` 列。
- 新增、编辑、详情必须使用弹窗承载；页面内不得长期展示新增/编辑表单作为完成态。
- 操作列固定在每行最右侧，动作命名统一为 `详情`、`编辑`、`新增子菜单`、`权限设置`、`启用/禁用` 等真实业务动作。
- 菜单管理必须以 `parentCode` 构建菜单树展示层级，支持根菜单新增、节点详情、节点编辑和子菜单新增。
- 角色权限设置必须进入专用弹窗，权限点按 code 前缀分组，菜单按同一菜单树展示；保存仍使用真实角色绑定接口。
- 租户模型配置、平台模型目录、租户、角色、权限、菜单均按同一 list/dialog primitive 实现，禁止每页独立发明一套交互。
- API Key 等敏感字段只允许输入和 last4 展示；编辑弹窗不得回显密钥明文。
- 宽屏控制台应减少无效左右留白，内容最大宽可放宽至 1680px，但必须保留稳定 gutter；1024 和 390 宽度仍不能出现整页横向溢出。

## 企业级设计原则

- 任务优先：首屏必须直接呈现当前操作上下文、主操作、关键状态和错误反馈，不做介绍型 hero、营销文案或装饰性指标。
- 信息密度：桌面 1280px 宽度下，主流程表单、表格和状态摘要应在首屏或首屏下方一屏内完成扫描；禁止用大卡片堆叠替代表格、列表和配置表单。
- 权限可见但不替代安全：前端只根据 `/api/auth/me` 返回的菜单和权限渲染入口、按钮禁用和状态提示；后端权限注解仍是唯一安全边界。
- 真实状态：loading、saving、success、error、disabled、empty、forbidden、readonly 必须有稳定样式；不得用静态成功文案掩盖接口失败。
- 视觉克制：使用中性色底、清晰分割线、少量品牌色和语义色；禁止大面积渐变、装饰光斑、营销型插画、嵌套卡片和过度圆角。
- 可维护：样式必须沉淀为 token、布局 primitives、表单、表格、按钮、消息、导航和状态组件规则；禁止每个页面临时写一套视觉样式。

## 信息架构

控制台固定为三层结构：

1. 应用壳：左侧 RBAC 菜单、当前租户/平台上下文、登出和全局状态。
2. 页面头：当前菜单标题、页面说明、主操作、最近一次错误或成功反馈。
3. 工作区：表单、表格、权限矩阵、配置详情、运行结果和审计/trace 摘要。

平台管理和租户平台可以共用应用壳，但页面内容必须区分：

| 区域 | 典型页面 | 设计要求 |
| --- | --- | --- |
| 平台管理 | 租户、角色、权限、菜单、模型基础配置 | 以表格、矩阵和配置表单为主，强调变更影响、状态和审计 |
| 租户平台 | 租户模型配置、后续知识库、应用和调用入口 | 以配置向导、运行状态、用量和错误诊断为主，禁止自由输入平台目录字段 |
| 运行时 | 后续 chat invocation、trace、usage | 必须呈现调用状态、模型、token、成本、traceId 和失败原因 |

## 设计 Token

首期不引入额外企业组件库，使用 Vue 3 + TypeScript + 原生 CSS 变量形成稳定 token：

| Token | 用途 | 默认规则 |
| --- | --- | --- |
| `--color-bg` | 页面背景 | 冷中性浅灰，不能偏营销奶油色 |
| `--color-surface` | 面板和表单底 | 白色或极浅灰，边界通过 1px border 表达 |
| `--color-text` | 主文本 | 深灰黑，保证表格和表单可读 |
| `--color-muted` | 次要文本 | 中性灰，不承载关键错误或权限信息 |
| `--color-primary` | 主操作和当前选中 | 克制蓝绿或蓝色，仅用于主按钮、焦点和当前菜单 |
| `--color-danger` | 错误和危险操作 | 红色语义色，只用于失败、禁用确认和高风险动作 |
| `--color-success` | 成功反馈 | 绿色语义色，只用于完成态提示 |
| `--radius-sm/md` | 控件圆角 | 4px / 8px；不得出现大胶囊式业务卡片 |
| `--shadow-panel` | 浮层或登录面板 | 仅用于真正浮层，不给普通页面 section 加强阴影 |

A2 默认 token 方向：

- `--color-bg`: `#f6f7f9`
- `--color-canvas`: `#fafbfc`
- `--color-surface`: `#ffffff`
- `--color-primary`: `#0f766e`
- `--radius-md`: `8px`
- `--sidebar-width`: `clamp(232px, 17vw, 272px)`
- `--content-max`: `1680px`
- `--page-gutter`: `clamp(14px, 1.2vw, 24px)`

## 布局规则

- 桌面端左侧菜单宽度控制在 220px 到 252px，内容区最大宽度控制在 1440px 到 1680px，避免宽屏出现过大无效留白。
- 移动端左侧菜单不得纵向占满首屏，必须切换为紧凑横向滚动导航或等价折叠形态。
- 页面 section 不做卡中卡；重复实体才使用卡片，配置、列表和矩阵优先使用 panel、table、row、field grid。
- 表单默认三列或两列网格，短字段同排，密钥、URL、长编码独占或允许跨列。
- 表格必须支持横向滚动和 row hover；字段编码、routePath、componentKey、modelCode 允许换行但不能溢出。
- 移动端不追求完整管理效率，但必须无横向页面溢出、无按钮文字裁切、无表单重叠。
- 所有固定格式元素必须有稳定尺寸，hover、loading、错误文案不能导致页面大幅跳动。

## 组件规范

### 导航

- 菜单事实源只能来自 `/api/auth/me`。
- 当前菜单必须有明确 selected 状态。
- 根菜单仅作为分组标题时不可被误认为按钮。
- 新页面如果没有 `menuCode`、`componentKey`、`routePath` 和 permission code，不得视为完成态。

### 按钮

- 主按钮只用于保存、创建、提交、运行等单一主动作。
- 次按钮用于连接测试、403 校验、启用/禁用等辅助动作。
- 危险动作后续必须有确认或等价保护，不得与普通次按钮同色。
- loading 和 disabled 文案必须解释当前动作，不使用空 spinner 替代。

### 表单

- label 必须可读并贴近输入框。
- readonly 字段必须明显区别于可编辑字段，避免租户误以为可自由修改平台目录字段。
- 密钥字段只输入不回显；响应只允许 last4。
- 保存成功和失败消息必须出现在当前表单附近，不能只放全局 toast。

### 表格和矩阵

- 表头使用小号高权重文本，行内容保持 14px 级别可读密度。
- 权限矩阵按权限点和菜单分区，长 code 可换行。
- 状态字段必须使用语义文本或状态徽标，不能只依赖颜色。
- 空数据必须有明确空状态和下一步动作，不能显示空白 panel。

### 运行态和错误态

- `403`、权限不足、接口失败、provider 额度不足、模型能力不匹配必须呈现可诊断中文信息。
- S5.1 调用入口必须显示 selected provider、modelCode、capability、traceId、latency、token/usage 或缺失原因。
- 任何模型调用或连接测试失败不得伪造成成功。

## S5.1 前端入口约束

S5.1 的前端范围只允许在后端统一调用 API contract 冻结后增加最小调用 smoke surface：

- 选择当前租户已配置的 chat 模型。
- 输入一条短 prompt。
- 显示调用中、成功、失败和权限不足状态。
- 显示 traceId、模型、延迟、usage/cost 基础字段。
- 不新增知识库、tool、数据库知识源、完整观测大屏或应用编排设计。

## 质量门禁

前端页面完成态必须同时满足：

- `pnpm --dir frontend/console-web test` 通过。
- `pnpm --dir frontend/console-web build` 通过。
- 真实后端页面 smoke 无控制台错误、接口错误和白屏。
- 桌面和移动宽度无主内容溢出、文字裁切和不可点击主操作。
- 至少验证 1440、1024、390 三类视口；如果某视口无法自动化验证，必须记录原因和人工截图证据。
- 页面使用本文件定义的 token、布局和状态规范。
- 新页面已注册菜单、权限和后端保护；按钮禁用只做体验增强，不替代接口权限。
- 设计复核由资深前端工程师和 UI 工程师共同确认；发现视觉系统漂移时先修复设计系统或控制面，再继续扩页面。
