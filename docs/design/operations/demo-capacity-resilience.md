# M1 演示环境容量与故障恢复运行手册

## 目的

本手册固定 M1 本地确定性模型环境的端到端可信查询容量门禁，并在隔离恢复环境演练
PostgreSQL、MinIO、查询运行时和摄取进程的停止与重启。演练不得直接停止源演示环境
的数据服务，也不得将结果外推为真实厂商模型或生产容量承诺。

## 测量边界

容量请求覆盖：

`认证会话 -> 已发布助手目录 -> 查询配额 -> 模型修订解析 -> 嵌入 -> 授权检索 ->
重排 -> 确定性生成 -> 引用验证 -> 查询事实、事件和用量持久化`

已有的候选池性能测试只测 PostgreSQL 内的二十条向量候选排序，用于定位检索内核退化；
它不替代本手册的端到端容量结果。

## 固定场景

- 环境：由源演示数据备份后创建的隔离恢复环境。
- 租户数：2。
- 每租户并发数：4。
- 总并发数：8。
- 每租户预热请求：5。
- 每租户采样请求：20。
- 总采样请求：40。
- 模型：本地确定性对话和嵌入模型。
- 数据：门店和校园合成知识、各自唯一的已发布助手。
- 请求：每次使用全新幂等键，禁止把历史重放计入容量。

## 通过门禁

- 错误率：0。
- 幂等重放数：0。
- 每条回答必须为已回答状态，包含引用和场景答案要点。
- 95 分位端到端耗时不超过 1000 毫秒。
- 总吞吐不低于每秒 5 次查询。
- PostgreSQL、MinIO、查询运行时和摄取进程均能停止后恢复健康。
- 全部服务重启后再次完成两个租户的端到端查询。
- 原演示环境保持健康，隔离容器、网络和卷全部清理。

## 执行

前置检查：

```bash
make project-status
make deploy-smoke
make capacity-resilience-operations-test
```

完整演练：

```bash
make capacity-resilience-demo
```

该命令将：

1. 生成临时机密备份并立即恢复到受控隔离环境。
2. 预热并执行两个租户的并发可信查询。
3. 依次停止并启动 PostgreSQL、MinIO、查询运行时和摄取进程。
4. 在重启后再次执行双租户查询。
5. 记录数据规模、硬件、Docker 版本、镜像内容摘要、分位值和吞吐。
6. 删除隔离环境与临时备份。
7. 生成不含秘密和业务正文的机器报告：
   `/private/tmp/ai-platform-operations/WP-0007-capacity-resilience.json`。

任何容量门禁、服务恢复、源环境健康或资源清理失败都会返回非零状态。

## 结果解释

- 结果只适用于报告中的本机硬件、Docker 版本、合成数据规模和确定性模型。
- 测试没有外部网络模型延迟、真实供应商限流或生产流量分布。
- 真实厂商接入后必须按模型、区域、流式方式和供应商配额重新建立容量基线。
- 单机演示恢复不等同于高可用；进程停止期间允许短暂不可用。
- 生产发布仍需独立完成持续压测、资源饱和点、稳定性时长和降级验证。

## 故障处置

演练只使用带 `trusted-rag-foundation-v1-recovery-` 前缀的隔离项目。若中途失败：

1. 保留当前终端错误，不复制令牌或响应正文到证据。
2. 检查隔离项目服务状态和日志。
3. 使用受控清理脚本删除确认属于本次演练的隔离资源。
4. 重新执行 `make deploy-smoke` 确认源环境健康。
5. 修复根因并从头执行完整演练，不手工改写成功报告。
