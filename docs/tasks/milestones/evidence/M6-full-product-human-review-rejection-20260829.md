## 评审范围与判定原则

本次评审覆盖平台管理员、租户管理员和普通用户三种产品角色，以及平台租户、平台账户、模型供应链、租户成员、知识数据、模型配置、助手发布、可信问答和全局界面体验。

本次结论以“用户能否从新建平台环境完成可理解、可授权、可恢复、可验证的核心任务”为判断基准，不以页面存在、接口存在、数据库有表、局部自动测试通过或旧环境中存在历史数据代替产品闭环。

当前人工操作已经直接证明：

- 平台模型连接可以建立，但模型发现失败，导致发现、探测、部署、目录发布和租户使用链路中断。
- 平台管理员、租户管理员和普通用户的账户所有权、成员候选、角色分配和资源授权边界仍不符合目标 SaaS 模型。
- 知识空间、数据来源、对象范围、模型目录、助手发布和普通用户问答之间没有形成可理解的连续任务。
- 多个分页页、表单、弹窗和空状态虽然可以渲染，但视觉质量、交互层级和任务说明不足以通过企业产品验收。
- 当前 RAG 实现尚无足够证据证明查询权限、检索准确率、引用真实性和拒答质量达到“可信”标准。

## 严重度定义

| 严重度 | 定义 |
| --- | --- |
| P0 | 阻断核心业务链、安全边界或产品价值，未关闭前不得再次申请 M6 人工评审。 |
| P1 | 核心管理任务可见但不可理解、不可稳定完成或明显不符合 SaaS 产品模型，未关闭前不得通过整体产品验收。 |
| P2 | 不直接阻断服务端核心行为，但显著降低操作效率、视觉质量、可访问性或产品可信度，须在再次人工评审前完成或取得明确接受。 |

## 一、平台模型供应链

### 2. 平台厂商连接列表的列宽与操作对齐不合格

| 字段 | 内容 |
| --- | --- |
| 严重度 | P1 |
| 当前事实 | “厂商与区域”列宽不足，厂商类型、区域和发现协议发生换行；操作列没有稳定右对齐，按钮与其他分页目录的视觉规则不一致。 |
| 产品判定 | 平台连接是高频治理目录，必须支持快速比较厂商、区域、发现方式、验证状态和下一步操作。当前表格不能形成稳定扫描路径。 |
| 退出证据 | 前端红绿测试覆盖列宽、操作对齐和窄屏恢复；真实 Chrome 在 1024×768、390×844 和真实 200% 缩放下无文档级横向溢出，厂商与区域信息保持可读，操作列稳定对齐；键盘可依次到达每个操作。 |
| 是否需 ADR | 否。属于 ADR-0059 和既有 Fluent UI 目录模式内的界面缺陷。 |

### 3. 厂商类型、发现协议与参数配置缺少受控对应关系

| 字段 | 内容 |
| --- | --- |
| 严重度 | P0 |
| 当前事实 | 新建平台连接允许用户分别选择厂商类型和模型发现协议，能够形成“火山方舟厂商语义却使用通用 OpenAI Models API”等无效组合。表单没有根据厂商自动确定 Endpoint、区域、凭据类型和发现方式。 |
| 产品判定 | 厂商选择必须代表一个明确的接入预设，而不是让管理员拼装底层协议。火山方舟控制面发现需要区域及独立 AK/SK；OpenAI-compatible 使用数据面 API Key 和 Models API。不同凭据不得混用，未知能力不得按名称猜测。 |
| 退出证据 | 表单仅暴露业务可理解的“接入预设”；选择火山方舟后自动固定控制面发现协议、官方基础地址、默认区域和 AK/SK 要求，API Key 仅用于推理探测；选择 OpenAI-compatible 后只显示对应基础地址和 API Key；前端测试证明不能产生非法组合；后端仍以权威适配器和受控凭据槽为最终事实。 |
| 是否需 ADR | 否。ADR-0070 已确定权威发现和独立凭据边界，本项是对既有决定的正确实现。 |

### 4. “验证并发现模型”失败，模型供应链主流程中断

| 字段 | 内容 |
| --- | --- |
| 严重度 | P0 |
| 当前事实 | 人工操作返回 `succeeded: false`，内部结果为 `OPENAI_COMPATIBLE_DISCOVERY_ENDPOINT_REJECTED`，模型候选为空。基础 Compose 未完整传递模型出站白名单和调用超时，且错误连接组合会进入不适用的发现适配器。 |
| 产品判定 | 该问题直接阻断“连接 → 发现 → 探测 → 部署 → 目录发布 → 租户使用”，属于当前第一修复优先级。页面只能展示安全、可行动的业务提示，不能向浏览器返回内部发现标识、适配器结果码、厂商原始响应或内部耗时。 |
| 退出证据 | 红绿 TDD 覆盖 Compose 出站边界、厂商预设分派和安全 HTTP 响应；真实 PostgreSQL 保存连接及凭据修订；真实 HTTP 完成发现请求；基础 Compose 明确传递 `MODEL_ALLOWED_ENDPOINTS` 和 `MODEL_CALL_TIMEOUT`；有受控真实凭据时完成供应商权威发现成功续证；无真实凭据时只能登记本地权威契约通过，不得声称外部供应商调用成功。 |
| 是否需 ADR | 否。属于 ADR-0070 已接受能力的阻断缺陷。 |

### 14. 租户模型配置与平台模型目录为空，模型分配产品逻辑不符合目标

| 字段 | 内容 |
| --- | --- |
| 严重度 | P0 |
| 当前事实 | 租户模型配置页的“当前模型配置”和“平台模型目录”均为空。目录数据依赖平台连接、发现、部署、探测和目录发布完整成功；当前供应链失败后没有可选模型。现有页面仍提供租户建立和轮换模型配置的表达，与“租户只能选择平台已开通模型”的目标不完全一致。 |
| 产品判定 | 平台管理员应负责连接、凭据、部署、探测和目录发布；租户管理员只能在平台已发布且当前可用的模型范围内选择用途，不应接触供应商连接、Endpoint、底层模型参数或平台凭据。 |
| 退出证据 | 以平台管理员完成连接、发现、部署、探测和目录发布；租户管理员页面只读取平台已发布、当前可用的目录；空状态说明缺少的是平台供应而不是要求租户自建连接；真实 PostgreSQL、HTTP 和 Chrome 证明停用或过期平台部署会从租户可选范围失效关闭；租户页面不展示或写入平台凭据。 |
| 是否需 ADR | 是。需要明确平台模型供应、租户用途分配、租户凭据是否完全退役以及现有模型配置聚合的迁移边界，并修订或补充 ADR-0058、ADR-0059、ADR-0065 和 ADR-0066。 |

## 二、平台租户、账户与角色治理

### 1. 建立租户管理员页面输入框不对齐且尺寸不一致

| 字段 | 内容 |
| --- | --- |
| 严重度 | P1 |
| 当前事实 | 租户建立第二步中的查找、登录名和初始口令输入区域没有统一栅格，字段高度、宽度、标签位置和操作按钮对齐不一致。 |
| 产品判定 | 租户入驻是平台管理员的关键高风险任务，必须形成稳定的步骤结构、字段组和提交层级，不能呈现为临时拼接表单。 |

### 5. 平台租户页面没有形成明确的分页目录

| 字段 | 内容 |
| --- | --- |
| 严重度 | P1 |
| 当前事实 | 页面只展示一条租户记录和底部分页文字，缺少稳定表头、列结构、分页容器和目录视觉层级，人工难以判断这是可扩展的服务端分页列表。 |
| 产品判定 | 平台租户应作为正式生命周期目录展示名称、编码、状态、最后变更和合法操作；即使当前只有一条数据，也必须保留完整目录结构和可理解的空页、单页、多页状态。 |

| 是否需 ADR | 否。ADR-0049 和 ADR-0059 已确定服务端分页和目录模式。 |

### 6. 租户管理员角色的分配方式缺少清晰反馈

| 字段 | 内容 |
| --- | --- |
| 严重度 | P1 |
| 当前事实 | 当前后端在新租户建立事务中会把选定主体自动建立为初始租户管理员，但页面没有清楚说明“租户建立成功即自动分配租户管理员”，导致人工继续寻找额外授权入口。 |
| 产品判定 | 初始租户管理员应由平台管理员在租户建立流程中明确选择或建立，并在提交确认和完成结果中显示自动授权事实，不应要求平台管理员建立租户后再进入租户成员页重复分配。 |
| 退出证据 | 租户建立确认页明确显示管理员账户和将获得的角色；真实 PostgreSQL 证明租户、初始管理员成员资格和角色绑定原子提交；登录后会话只得到目标租户管理员能力；失败时三项事实均不落库；Chrome 完成从平台建立到租户管理员首次登录。 |
| 是否需 ADR | 否。沿用 ADR-0042 和 ADR-0047 的初始管理员原子分配语义，只需补齐产品反馈。 |

### 7. “管理成员内置角色”弹窗过于简陋

| 字段 | 内容 |
| --- | --- |
| 严重度 | P1 |
| 当前事实 | 弹窗把当前角色、撤销操作、新增角色选择和提交按钮平铺在较小区域内，缺少成员身份摘要、权限影响、会话撤销说明、当前与可选角色分区以及高风险操作确认。 |
| 产品判定 | 角色变更会改变权限并立即撤销旧会话，必须采用清晰的信息层级和单一决策，不得在一个弱结构弹窗中同时混合分配与撤销。 |
| 退出证据 | 使用单一 Fluent UI Dialog 或独立任务路由，分别呈现成员摘要、当前角色、可分配角色、权限影响和会话影响；撤销使用二次确认；写后重读服务器事实；键盘、Escape、焦点恢复、390×844 和真实 200% 通过。 |
| 是否需 ADR | 否。若角色所有权按第 8、9 项改变，则实现需等待对应新 ADR。 |

### 8. 平台管理员对租户管理员账户和权限的治理职责不完整

| 字段 | 内容 |
| --- | --- |
| 严重度 | P0 |
| 当前事实 | 平台管理员可以在租户建立时选择或建立初始管理员，且角色会自动分配；但租户建立后的租户管理员账户停用、替换、追加和角色治理主要落在租户成员管理路径，平台侧没有完整生命周期任务。 |
| 产品判定 | 平台管理员应拥有租户建立、初始管理员分配、租户管理员追加或替换、停用影响检查和恢复入口；租户管理员不应自行提升或治理同级租户管理员。 |
| 退出证据 | 新 ADR 明确平台与租户的管理员所有权；平台侧完成租户管理员目录、分配、替换、停用影响检查、最后管理员保护和全会话撤销；真实 PostgreSQL、HTTP 和 Chrome 证明平台操作原子、失败关闭且不授予租户正文读取能力。 |
| 是否需 ADR | 是。该决定改变 ADR-0057、ADR-0067 下现有租户角色绑定和成员生命周期所有权。 |

### 9. 当前租户管理员权限过大，不符合 SaaS 租户边界

| 字段 | 内容 |
| --- | --- |
| 严重度 | P0 |
| 当前事实 | 当前后端允许租户管理员绑定或撤销 `TENANT_ADMINISTRATOR`，并可停用其他租户管理员，仅有最后访问管理员保护。租户管理员成员候选和操作范围没有收敛为本租户普通成员。 |
| 产品判定 | 目标 SaaS 模型中，租户管理员只能管理本租户普通人员，并为普通成员分配可使用的数据和功能范围；租户管理员账户本身的建立、停用和管理员角色分配由平台治理。 |
| 退出证据 | 新 ADR 固定平台管理员和租户管理员的所有权；服务端拒绝租户管理员建立、停用、提升、降级或撤销任何租户管理员；租户管理员只能操作本租户普通成员；跨租户、同级管理员、平台账户和最后管理员场景全部以真实 PostgreSQL、HTTP 和旧会话撤销测试失败关闭。 |
| 是否需 ADR | 是。必须以新 ADR 修订现有三角色成员治理语义，不能只隐藏前端按钮。 |

### 10. 新建租户成员弹窗质量低且错误显示平台 `admin` 账户

| 字段 | 内容 |
| --- | --- |
| 严重度 | P0 |
| 当前事实 | 新建成员弹窗结构简陋，搜索、单选、分页和提交缺少层级；候选查询只排除当前租户已有成员，没有排除平台管理员或不符合租户成员资格的账户，因此显示 `admin`。 |
| 产品判定 | 租户成员候选只能包含允许加入当前租户的活动普通账户。平台管理员、停用账户、其他受限管理身份和已有成员不得出现；服务端必须执行同一资格校验，不能只靠前端过滤。 |
| 退出证据 | 候选资格在领域／应用和 PostgreSQL 查询中统一；真实 HTTP 证明平台管理员、停用账户和已有成员均不返回，伪造目标提交同样拒绝；弹窗重构后具备搜索结果摘要、空状态、明确选择、分页和提交状态；完成窄屏、200%、键盘和焦点恢复续证。 |
| 是否需 ADR | 是。界面重构本身不需 ADR；候选资格和租户管理员只能管理普通成员的语义与第 8、9 项共用新 ADR。 |

## 三、知识空间与数据来源生命周期

### 11. 数据任务页面重复提供“退出登录”

| 字段 | 内容 |
| --- | --- |
| 严重度 | P2 |
| 当前事实 | 受治理文件来源等页面在内容区同时展示“刷新”和“退出登录”，而右上角账户区域已经承担会话身份和全局账户操作。 |
| 产品判定 | 退出登录是全局会话动作，应只存在于统一账户菜单。任务页面只保留与当前任务直接相关的刷新、建立、探测、发布和恢复操作。 |
| 退出证据 | 所有业务内容页移除重复退出入口；统一右上角账户菜单提供退出；跨平台和租户工作区一致；键盘可到达并在退出后撤销会话、回到登录入口。 |
| 是否需 ADR | 否。属于统一产品壳和注意力保护整改。 |

### 12. “发布首份知识数据”混淆知识库创建与数据发布

| 字段 | 内容 |
| --- | --- |
| 严重度 | P0 |
| 当前事实 | 页面以“首份文本发布”为任务名称，在一个向导中隐式验证租户、确定或创建知识空间、上传文本、发布和构建索引。用户离开后难以恢复既有来源，知识空间、知识库、数据源、发布产物和索引之间的关系不清楚。 |
| 产品判定 | 产品应先显式创建知识库或知识空间，再在该知识库内添加文件、结构化数据或对象范围，完成探测、同步、质量、发布和索引。首次引导可以存在，但不能成为唯一入口或隐藏正式生命周期。 |
| 退出证据 | 新 ADR／设计明确知识库、数据源、发布产物和索引的所有权与状态；页面提供“创建知识库 → 添加数据源 → 处理与质量 → 发布 → 建立索引”的可恢复路径；刷新、离开和重新进入不会重复已完成操作；真实 PostgreSQL、MinIO、HTTP、工作器和 Chrome 完成新建及恢复任务。 |
| 是否需 ADR | 是。需要冻结知识库、数据来源、发布和索引生命周期以及首次引导与正式管理入口的关系。 |

### 13. 对象存储范围登记的来源、授权和表单逻辑不清楚

| 字段 | 内容 |
| --- | --- |
| 严重度 | P1 |
| 当前事实 | 知识空间和已授权对象范围使用下拉选择，却在字段下方重复展示分页控件；“来源名称”实际为文本输入，不是下拉。可选对象范围来自部署配置中的受控对象范围，目前没有平台 UI 或公开管理 API，默认环境因此为空。 |
| 产品判定 | 平台管理员应先配置并验证对象存储连接和可授权范围；租户管理员只能在当前租户、知识库已获授权的范围中选择，并为登记的数据源填写业务名称。下拉选择不应伪装成分页目录；大集合应使用可搜索选择器或独立选择任务。 |
| 退出证据 | 新 ADR 明确对象存储连接、平台范围、租户授权和知识库登记四层所有权；平台提供受控配置和验证入口；租户页面只返回脱敏范围名称和状态，不返回桶名、对象键、Endpoint 或凭据；真实 PostgreSQL、对象存储、HTTP 和 Chrome 覆盖零项、单项、多页搜索、未授权和失效范围。 |
| 是否需 ADR | 是。当前只有部署配置，新增平台管理、租户授权和失效传播会改变公共契约和安全边界。 |

## 四、普通用户问答与可信 RAG

### 15. 普通用户没有可到达的 RAG 问答入口

| 字段 | 内容 |
| --- | --- |
| 严重度 | P0 |
| 当前事实 | 代码中存在 `/ask` 和查询运行能力，但当前统一 SPA 没有完整的助手建立、版本冻结、评测、发布和普通用户助手目录任务。新环境无法从零产生可供普通用户使用的已发布助手，因此“问答”菜单不能证明普通用户能够完成 RAG 问答。 |
| 产品判定 | 租户管理员必须能够选择知识库、模型和检索策略建立助手，完成测试、评测和发布；普通用户只看到自己获授权的已发布助手，并能提问、查看引用、识别拒答和提交反馈。 |
| 退出证据 | 新 ADR 明确助手草稿、版本、模型／知识库绑定、评测、发布和用户授权；从空库完成“平台模型发布 → 租户知识库索引 → 助手建立与发布 → 普通用户登录 → 问答、引用、拒答、反馈”真实纵向闭环；直接 URL、跨租户、未发布助手和未授权知识均失败关闭。 |
| 是否需 ADR | 是。已有底层查询能力不足以确定完整助手产品生命周期和普通用户资源授权。 |

### 18. RAG 查询权限和准确性没有达到可信验收标准

| 字段 | 内容 |
| --- | --- |
| 严重度 | P0 |
| 当前事实 | 当前实现具备租户上下文、向量检索、引用、拒答、反馈和部分评测基础，但没有足够产品级证据证明成员资源授权在候选检索前生效，也没有绑定数据集版本、索引版本、模型版本和检索参数的稳定准确率基线。 |
| 产品判定 | “可信 RAG”必须同时证明权限正确和回答质量。资源授权过滤必须在候选进入排序和生成前失败关闭；质量不能以单次演示或主观回答代替，必须使用冻结评测集持续验证检索召回、排序、引用真实性、答案忠实度、拒答和越权率。 |
| 退出证据 | 新 ADR 固定资源授权过滤顺序、助手可见范围、评测数据治理和发布质量门禁；建立冻结黄金集，记录 Recall@K、nDCG@K、MRR、引用命中率、引用支持率、答案忠实度、拒答准确率、越权命中率、延迟和成本；证据绑定数据集、索引、Embedding、Chat 模型及参数版本；跨租户、无授权、提示注入、错误引用和无答案场景全部失败关闭。 |
| 是否需 ADR | 是。需要新增可信 RAG 权限过滤与质量发布门禁 ADR，不能只增加前端指标。 |

## 五、信息架构、组件系统与视觉质量

### 16. 全平台菜单缺少父子层级，页面任务不够聚焦

| 字段 | 内容 |
| --- | --- |
| 严重度 | P2 |
| 当前事实 | 当前侧栏把运营总览、成员与权限、数据、模型、治理和问答作为平级入口，数据和模型内部再以页签承载多个任务。随着平台治理、知识库、助手和评测功能增加，平级入口无法表达资源上下文和任务关系。 |
| 产品判定 | 应按角色和任务采用有限的父子菜单：平台治理下包含租户、账户和模型供应链；知识管理下包含知识库、数据来源、处理与索引；AI 应用下包含助手、评测和发布；普通用户只看到已授权问答和历史。菜单仍由服务端能力投影裁剪，不能代替权限。 |
| 退出证据 | 信息架构设计卡覆盖三种角色的导航树、面包屑、当前资源上下文和移动端导航；路由可直接访问和刷新恢复；无授权菜单不显示且直达仍由服务端拒绝；1024×768、390×844、200% 和键盘导航通过。 |
| 是否需 ADR | 否。只调整导航和路由组织时属于 ADR-0005、ADR-0048、ADR-0068 范围；若改变角色能力或资源授权则须使用对应新 ADR。 |

### 17. 全平台 UI 缺少现代感、科技感和企业产品完成度

| 字段 | 内容 |
| --- | --- |
| 严重度 | P1 |
| 当前事实 | 多数页面仍是基础标题、分隔线、表格、表单和默认弹窗的组合；空状态、危险操作、分页、数据密度、视觉层级和任务反馈不统一。现有局部重构没有达到整个平台一致的高质量水平。 |
| 产品判定 | 继续以 Fluent UI React v9 为唯一视觉组件系统，不进行全站组件库替换。Fluent 适合当前企业治理、无障碍和高密度任务；现代感应来自令牌、布局、信息层级、状态、微动效和数据可视化，不应通过混入第二套组件系统制造。设计参数采用 `DESIGN_VARIANCE: 7`、`MOTION_INTENSITY: 5`、`VISUAL_DENSITY: 6`，并在 `prefers-reduced-motion` 下关闭非必要动效。 |
| 退出证据 | 建立统一颜色、间距、圆角、阴影、排版、状态、表格、表单、Dialog、Drawer、空状态和骨架规范；所有重点页面完成视觉红绿测试与真实 Chrome 续证；无第二套视觉组件库；若未来出现十万级行数、二维虚拟化、复杂分组或导出等明确需求，先完成产品基准和 ADR 再评估 TanStack Table、React Aria、MUI X 或 AG Grid 专项接缝。 |
| 是否需 ADR | 否。保留 Fluent UI 符合 ADR-0005。若替换 Fluent UI、引入第二套视觉组件库或引入改变交互契约的专项 Grid，则必须先有新 ADR。 |

## 六、里程碑整体判定

### 19. 整个平台人工验收不合格

| 字段 | 内容 |
| --- | --- |
| 严重度 | P0 |
| 当前事实 | 当前系统存在模型供应链阻断、角色所有权冲突、知识生命周期不清、对象范围无管理入口、租户模型分配不完整、助手发布和普通用户问答不可达，以及多项全局 UI 质量问题。局部自动测试和历史浏览器证据无法证明当前空库环境中的核心价值闭环。 |
| 产品判定 | M6 不通过，`WP-0014` 继续进行，M7 保持阻断。交由人工复验前，必须先证明核心业务正确、权限安全、数据和模型供应可用、普通用户可以完成可信问答，并达到统一的高质量 UI 水准。 |
| 退出证据 | 所有 P0 和 P1 项关闭；P2 项关闭或取得人工明确接受；当前提交执行完整 `make validate` 和 `make project-verify`；最终源码 Compose 七服务健康；以真实 Chrome 完成三角色从零主流程、1024×768、390×844、真实 200%、键盘和 `prefers-reduced-motion`；另建独立 M6 人工批准记录。 |
| 是否需 ADR | 否。该项是人工里程碑决定；其中涉及公共权限、领域生命周期和资源授权的整改分别按前述新 ADR 执行。 |

## 必须新增的决策包

本次拒绝不直接接受尚未写入仓库的公共契约。以下问题在实施前必须分别形成可评审 ADR：

1. 平台拥有租户管理员生命周期，租户管理员只能管理本租户普通成员，并定义多个租户管理员、最后管理员保护、跨租户成员资格和旧会话撤销。
2. 平台模型供应与租户模型用途分配，明确租户是否完全退役自有模型凭据和配置轮换。
3. 知识库、数据来源、发布产物和索引的正式生命周期，以及首次引导与可恢复日常管理路径。
4. 对象存储连接、平台范围、租户授权和知识库登记的四层所有权及脱敏边界。
5. 助手草稿、版本、模型／知识库绑定、评测、发布和普通用户资源授权。
6. 可信 RAG 的检索前权限过滤、冻结评测集、质量指标和发布门禁。

上述 ADR 未接受前，只允许修复不改变公共语义的缺陷，不得通过隐藏按钮、前端过滤或直接数据库写入绕过决策。

## 下一阶段执行顺序

1. 立即修复平台模型发现阻断，关闭 Compose 出站配置、厂商预设、权威适配器分派和浏览器安全响应。
2. 完成租户管理员所有权与普通成员授权 ADR，再实施平台和租户成员治理重构。
3. 完成知识库、对象范围和平台模型分配 ADR，建立可恢复的数据与索引任务。
4. 完成助手发布和普通用户授权 ADR，打通从平台模型到普通用户问答的纵向闭环。
5. 在 Fluent UI v9 内执行全平台视觉与信息架构重构，使用已确定的设计方差、动效强度和信息密度参数。
6. 建立可信 RAG 权限与质量基线，完成真实数据、模型、索引、引用、拒答和越权评测。
7. 执行完整自动门禁、Compose、HTTP 和 Chrome 续证后，再申请独立人工评审。

## 退出条件

只有同时满足以下条件，才允许新建 M6 人工评审请求：

- 平台管理员能够从空库完成租户、租户管理员、平台模型连接、权威发现、部署、探测和目录发布。
- 租户管理员只能管理本租户普通成员，能够建立知识库、登记已授权数据来源、发布索引、建立并发布助手。
- 普通用户能够看到获授权助手，完成问答、引用核验、拒答识别和反馈。
- 模型、数据、助手和成员的失效、停用、越权及旧会话场景全部失败关闭。
- RAG 证据绑定数据集、索引、模型、参数和权限版本，并达到新 ADR 确定的质量门槛。
- 全平台 UI 达到统一的信息层级、响应式、可访问性和视觉质量标准。
- 真实 PostgreSQL、Redis、MinIO、HTTP、工作器、Compose 和全量工程门禁通过。
- 真实 Chrome 完成 1024×768、390×844、真实 200%、键盘导航和 `prefers-reduced-motion` 续证。
- 人工明确签署新的 M6 通过记录。

本记录覆盖并扩展 `M6-human-review-rejection.md` 中仅针对登录页的旧拒绝范围。旧技术证据不被删除，但任何旧证据均不得被解释为当前全产品已经获得人工接受。`M6` 和 `WP-0014` 保持进行中，`M7` 必须保持未激活。
