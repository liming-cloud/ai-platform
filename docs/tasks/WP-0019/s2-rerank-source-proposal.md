## 需要决定的范围

用户已接受硅基流动 `BAAI/bge-reranker-v2-m3` 与预算方向，但这不自动建立平台候选或授权真实调用。本提案决定它如何取得可审计的来源，不建立部署、发布或租户授权，不替代三样本的真实 RERANK 验证。

源码中 `PlatformProviderPresets#variant` 将 RERANK 冻结为 `VENDOR_POST_PROCESSOR + NONE`，包括硅基流动、百炼和自定义预设。`PlatformProviderModelDiscoveryService#discover` 按协议／发现配置选择扩展；没有对应扩展时产生 `PLATFORM_MODEL_DISCOVERY_UNSUPPORTED`，不会形成成功的当前发现。`PlatformModelDeploymentService#create` 又要求当前连接已验证、已独立发布且具有当前候选。因此仅录入 Key、手填模型编码或向静态列表补一行，都不能闭合正式创建路径。

ADR-0070 对 NONE 要求受控目录，不能把“不支持发现”记为成功。静态目录只证明平台声明，既不证明当前账户可访问，也不能直接写 VERIFIED；否则会绕过当前连接验证／发布边界。现有实例不回填候选，不改写旧 NONE 的发现结果或修订。

## 核实后的方案比较

| 方案 | 优点 | 代价与风险 | 结论 |
| --- | --- | --- | --- |
| NONE 加版本化静态目录 | 可确定性审阅模型与协议 | 仍缺账户级只读验证；若直接把目录装载当连接验证，会产生虚假 VERIFIED。还需另立 NONE 连接发布与后续真实验证合同 | 保留为真正无权威列表厂商的后续设计，本轮不伪造完成 |
| 硅基流动使用显式官方重排列表来源 | 用账户 Key 只读查询，复用当前发现／发布／草稿顺序，无需新增云端资源 | 需接受独立发现配置、厂商预设新版本及旧 NONE 的显式修订方式；列表成功仍不是重排能力成功 | **推荐，仅限硅基流动 RERANK** |
| 管理员自由录入模型编码后直接建草稿 | 表单少 | 无权威来源、修订和失效事实，绕过 ADR-0070；仍无法证明账户能力 | 不采用 |

新的一手事实是硅基流动[官方 List Models](https://docs.siliconflow.cn/docs/api/models-get)明确支持 `sub_type=reranker`，使用 Bearer 认证，返回 `data[].id`。因此该厂商并非完全没有权威只读列表；当前 NONE 是本仓库的预设状态，不能据此推断厂商没有此接口。本轮只阅读公开文档，未使用用户 Key 查询厂商。

## 推荐合同（待接受）

1. **显式来源。** 为硅基流动重排增加明确的发现配置 `SILICONFLOW_RERANK_MODELS_API`；保留运行协议 `VENDOR_POST_PROCESSOR` 和 `ProviderKind` 的既有意义。不把通用 `OPENAI_MODELS_API` 偷换为重排，不按域名或名称选择适配器。其他 NONE 预设维持不可发现；不对百炼、自定义连接外推支持。
2. **固定只读请求。** 预设版本决定只读目标 `GET https://api.siliconflow.cn/v1/models?sub_type=reranker`；不是把用户输入的 `/rerank` 字符串裁剪后猜测列表地址。沿用当前连接的平台推理 Key，先出站验证、再短期解析秘密，完成后关闭。无推理、无云资源创建、零自动重试；拒绝重定向、私网、超时、畸形／过大响应。读取只授予当前账户的列表可见性事实。
3. **候选来源与分类分别冻结。** 当前成功响应必须包含精确 `id` 才能形成该账户当前候选；公开官方模型说明及版本化受控映射为 `BAAI/bge-reranker-v2-m3` 指定 RERANK，分类为 `CONFIRMED_BY_CONTROLLED_MAPPING`。映射不存在的官方列表项保留为 `REQUIRES_ADMIN_CONFIRMATION`，不按名称猜测，也不静默丢弃。显示名称缺失保持未知，供应商编码只作选择值。映射只声明协议与意图，不声明模型实际可用。
4. **不可变追溯。** 候选冻结连接 ID／精确修订、发现 ID／配置、供应商编码、候选分类、列表来源、受控映射版本／摘要、读取时间和失效时间。映射包含官方协议依据、类型和本次候选数 3 的验证意图，不把官方最大值当实测参数。不保存原始响应、认证头、凭据引用、外部追踪 ID 或 Endpoint 到普通投影。输入快照和创建事务需要可恢复这些来源绑定；新增必要字段先登记 ADR 及迁移反例，不静默塞进现有参数说明文本。
5. **正式链路与权限。** 仍由平台写权限发起发现，成功读取产生当前连接的发现验证，单独授权后发布精确连接修订，再从候选建立部署草稿。列表为空可以是成功的空集合，但不能提供不存在的模型或建立部署。该发现只证明已读取列表，不表示 RERANK 推理、三安全样本、费用或部署发布通过。之后仍需独立 RERANK 端口、精确真实调用许可和能力验证。
6. **旧对象处理。** 预设版本递增；新增连接使用新组合。已有 NONE 连接不自动升级、不回填、不过写历史。若要沿用某个旧连接，须另行允许一次显式发现配置修订，推进连接版本并使旧发现、确认和验证失效；本轮未授权此操作。首条验收优先另建合成连接，不改变已有业务对象；新建／发现／精确发布分别核对授权，不能从本提案接受外推。
7. **失效与恢复。** Key 轮换、来源修订、映射版本变化、发现过期／失败、连接停用均使后续新草稿失败关闭。一个真实空列表不能被旧候选补齐；旧修订结果不能覆盖当前发现。401／403／429、权限不足与厂商失败使用稳定类别，不把错误正文、Key 或签名记入证据。

采用官方列表的方案是在调查后提出的替代建议，尚未改变 ADR-0070 的 NONE 语义；接受后须先登记专属 ADR，再改预设、扩展和必要存储。若选择继续保留硅基流动 NONE，则必须先补齐静态目录之外的真实账户验证／发布合同，不能直接实现本文推荐路径。

## 实施前反例与验收

- 精确硅基流动 RERANK 预设／配置正例；其他厂商、旧 NONE、错区域、错来源版本、错模型或非平台会话均拒绝。
- 空列表不造候选；重复 ID、结构错误、超界响应、重定向、SSRF、429／超时不保留旧成功，未知模型不猜测不丢弃。
- 当前连接／发现／映射的绑定可以恢复；轮换、并发、迟到或审计失败在真实 PostgreSQL 中回滚，不留下候选或发布半成品。
- 本机协议反例之后再请求最小只读厂商验收许可；列表通过后仍单独准备真实重排调用，不能用发现证据替代能力验证。
- 扩展只依赖公开 port/out 与 facade，核心不引入 SDK 或跨上下文环。沿用已接受 S2 模型选择与详情；若新增来源说明改变原型正文或交互，先在原项目形成候选并单独接受，不改原型迁就代码。

供应商重排请求依据[官方 Rerank 协议](https://docs.siliconflow.cn/docs/api/rerank-post)：独立 `/v1/rerank`、query、documents、top_n、return_documents 及结果索引／得分。它支持当前选定模型，但文档并不证明本账户有权限或适用价格。预算、安全样本与剩余条件统一见[受控能力验证方案](s2-capability-verification.md)，不在本提案重复维护状态。
