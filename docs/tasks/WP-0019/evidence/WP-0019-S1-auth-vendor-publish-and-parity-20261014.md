## 目标、授权与登录来源

回顾 Charter、ROADMAP、STATE、本包及所引 ADR 后，本轮唯一目标仍为 S1，不进入 S2。复用有效授权和现有来源，解决登录及厂商验收阻断，验证最新部署，分别记录功能、视觉与切片完成结论。

用户已授权限定查找 `/private/tmp` 中本项目既有 0600 验收文件、使用现有登录来源、通过正式接口复用现有连接执行最小模型发现。另于本轮批准仅将 `ark.cn-beijing.volces.com` 加入本机 fake-IP 排除名单；发现成功后，又单独批准仅发布连接 `2093675537095458817` 的已验证修订 `4`。发布授权不包含模型部署、租户授权或新连接。

此前两个初始化环境候选各自 401 的结果保留在[前轮证据](WP-0019-S1-acceptance-blockers-and-prototype-empty-20261014.md)。本轮源码及只读主体事实确认本地管理员初始化遵循已接受 ADR-0071：`deploy/.env` 的候选并非现存本地账户的有效来源。复用仓库已登记的本地演示来源和既有租户验收来源，生成当前用户独占的 0600 临时文件，正式平台和租户登录均通过。没有修改登录合同、重置密码、读取密码摘要或探查浏览器会话；不再要求人工提供平台密码。

一次读取测试源码内凭据的尝试被自动审批拒绝，没有执行；随后改用已授权的标准本地来源。凭据内容、Cookie、Token、密码及其摘要均不进入报告、提交和产物摘要清单。

## 网络阻断与真实厂商事实

阻断机制是本机 Clash Verge / mihomo 的 fake-IP：主机及后端容器将方舟域名解析为 `198.18.0.0/15`，现有 SSRF 校验正常拒绝保留网段；它不是厂商认证失败。排除前加密 DNS 查询已返回公网地址。

按精确域名授权，仅追加该域名至现有黑名单模式的 fake-IP 排除集合，并用原本默认的全局增强脚本保持重生成后的同一排除。现有 DNS 覆盖开关仍关闭，原代理、规则、TLS、SSRF、端口及其他运行选项保留。mihomo 配置检查通过，七项增强脚本反例及幂等检查通过，标准本机配置接口热加载返回 204；没有重启 Docker、后端或清除 DNS / 业务缓存。后续主机及 control-plane 查询均为公网 1、保留网段 0。对应机制见[官方 DNS 配置](https://wiki.metacubex.one/config/dns/)和[配置热加载接口](https://wiki.metacubex.one/api/)。
