# 可信 RAG 基座交付计划

## 1. 交付原则

- 先冻结产品、领域、契约、交互和质量边界，再开始绿地实现。
- 每个工作包交付可独立验收的纵向闭环，不按前端、后端或数据库层拆成孤立任务。
- 每个角色同时最多负责一个进行中的工作包。
- 日期不能替代退出条件，代码不能替代证据。
- 演示站点用于证明基座闭环和暴露风险，不宣称生产就绪。
- 旧系统不进入启动、运行、测试、部署和数据路径。

## 2. 团队配置

| 角色 | 一人职责 | 首周主要产物 |
| --- | --- | --- |
| 产品 | 章程、任务、范围、配额、验收和评审 | 场景脚本、验收记录、范围决定 |
| 设计 | 信息架构、任务流、状态、原型和可访问性 | 六区导航、关键流程、状态规范 |
| 前端 | 页面、权限展示、流式交互、性能和可访问性 | 数据、模型、助手、问答与诊断闭环 |
| 后端 | 领域、接口、模型运行时、检索、数据和安全 | 三进程骨架与纵向能力 |
| 测试 | 测试策略、评测集、回归、性能和证据 | 契约、权限、RAG、容量报告 |
| 运维 | Docker、流水线、密钥、监控、备份和恢复 | 可重复部署、观测和恢复演练 |

产品负责人拥有目标与范围批准权；技术与安全例外需要对应负责人共同签署，不能由实现人员单独放行。

## 3. 分支与工作包

```text
master
  └── codex/trusted-rag-foundation-design
        └── 人工通过 M0 设计评审
              └── codex/trusted-rag-foundation-v1
                    ├── 按工作包创建短期分支
                    └── 通过证据门禁后合并
```

- `codex/trusted-rag-foundation-design` 只承载 M0 设计和治理控制面。
- 设计评审未通过前不得创建实施分支。
- 评审通过后，从被验证的设计提交创建 `codex/trusted-rag-foundation-v1`。
- 每个工作包声明目标、范围、负责人、分支、契约变化、验证命令、证据和下一前沿。
- 公共接口、领域边界、权限、模型能力或数据结构变化必须先有 ADR。

## 4. M0：设计冻结

### 4.1 进入条件

- 目标用户、参考场景和绿地边界明确。
- 技术基线和一周演示约束明确。
- 六个角色的职责和人工批准人明确。

### 4.2 退出条件

- 章程、路线图、状态、决策、追踪、风险、工作包和证据索引齐全。
- 产品、前端、领域、后端、接口数据和交付设计完成。
- 每个章程目标能追踪到工作包、测试和预期证据。
- 技术版本均为正式 GA，版本真实性在实施前再次核验。
- 人工评审明确记录通过、修改或拒绝。
- `make project-verify`、`make project-status` 和 `make resume-context` 通过。

### 4.3 人工评审清单

- 平台基座是否避免把门店或校园固化为核心领域。
- 一周演示是否形成数据、模型、助手、查询、引用、审计和用量闭环。
- 权限是否在检索前和生成前执行。
- 模型能力、路由和参数是否能扩展而不泄漏厂商类型。
- 前端是否按用户任务组织，而不是后端功能菜单。
- 每项非功能目标是否有可执行验证和证据位置。
- 是否明确排除了旧系统兼容、迁移和依赖。

## 5. M1：一周可部署演示

一周从 M0 人工通过、实施分支创建且环境准备完成后的第一个工作日开始。

### 第 1 天：可启动的纵向骨架

**共同结果：** 全新工程可由 Docker Compose 启动，用户可登录受限租户并看到与角色一致的导航。

- 产品：冻结演示任务、合成数据、配额和成功脚本。
- 设计：交付应用框架、登录、概览、空状态和错误状态。
- 前端：按详细目录规划建立 npm 工作区、`console-web`、`query-web`、必要共享包、路由、认证壳和权限裁剪。
- 后端：按详细目录规划建立根 POM、平台机制、六个 M1 上下文、首批扩展、三个运行入口和架构测试。
- 测试：建立源码内单元测试，以及根 `verification/` 的契约、验收、安全和评测骨架。
- 运维：建立 `deploy/compose`、每运行入口独立镜像、健康检查、环境模板和流水线。

退出证据：目录与依赖门禁通过；全新数据库和 Redis Key 空间启动；旧服务全部停止后系统仍可运行；三个运行入口和两个前端应用可独立构建。

### 第 2 天：租户、权限与模型连接

**共同结果：** 租户管理员能安全配置 OpenAI Compatible 或 Ollama 连接并完成探测。

- 产品：确认角色、设备范围、探测错误和凭据生命周期。
- 设计：交付模型四步流程和权限反馈。
- 前端：完成供应商连接、只写凭据、探测结果和模型部署页面。
- 后端：完成租户上下文、Sa-Token 适配、Vault 引用、地址策略、两类连接和探测。
- 测试：完成租户越权、密钥泄漏、SSRF 和厂商 WireMock 契约测试。
- 运维：配置开发密钥适配器、出站策略和脱敏日志。

退出证据：凭据不进入数据库和响应；禁止地址被拒绝；两类协议探测有可复核结果。

### 第 3 天：数据到已发布索引

**共同结果：** 知识管理员能导入门店或校园合成数据，检查质量并发布索引。

- 产品：确认数据含义、结构、敏感级别和新鲜度。
- 设计：交付数据源、同步检查、部分成功和发布流程。
- 前端：完成文件、数据集结构、同步报告和索引发布页面。
- 后端：完成对象存储、解析、受控数据集结构、切片、嵌入和索引版本。
- 测试：完成格式、重复、过期、越权、幂等和嵌入维度隔离测试。
- 运维：配置对象存储、向量存储、任务队列和资源限制。

退出证据：首次同步不自动发布；索引绑定固定嵌入模型与维度；失败可安全重试。

### 第 4 天：助手到可信回答

**共同结果：** 助手负责人能绑定知识和模型，演示用户能获得带引用回答或明确拒答。

- 产品：冻结门店和校园各自的问答脚本与拒答案例。
- 设计：交付助手草稿、测试、回答、来源和查询诊断。
- 前端：完成助手配置、问答、SSE 状态、引用、反馈和诊断。
- 后端：完成查询流水线、结构化查询语言、混合检索、重排、证据再鉴权、生成和引用验证。
- 测试：完成权限过滤、字段遮蔽、引用正确、无证据拒答、流式取消和回退测试。
- 运维：建立查询、模型、检索、Token、费用和延迟指标。

退出证据：无授权证据不能进入生成；每个事实声明可定位来源；撤权能阻止后续受保护访问。

### 第 5 天：评测、限量发布与恢复

**共同结果：** 助手通过固定评测后发布，演示站点按配额对外开放并能恢复。

- 产品：执行完整演示验收并记录限制说明。
- 设计：完成可访问性、窄屏、加载、空、错误、拒绝、部分和过期状态验收。
- 前端：修复阻断问题，完成性能与可访问性检查。
- 后端：完成评测门禁、审计、用量、配额、设备凭据和发布动作。
- 测试：执行回归、RAG 评测、性能、安全和故障演练。
- 运维：执行全新部署、备份、恢复、回滚和镜像摘要登记。

退出证据：演示脚本通过；配额不可绕过；备份恢复成功；发布镜像、提交和配置版本可追踪。

## 6. M1 功能验收

必须证明：

- 一个全新租户可以独立完成配置。
- OpenAI Compatible 和 Ollama 均通过统一 Chat、Embedding 契约。
- 文件与结构化数据集都能形成已发布索引。
- 门店和校园数据只通过通用结构与配置表达。
- 助手版本在评测通过后才能发布。
- 查询具备认证、配额、策略、权限过滤、检索、重排、证据再鉴权、生成、引用、审计和计量。
- 回答能够显示来源；证据不足、过期、无权或模型能力不足时安全拒答。
- 演示账号每日、每分钟、并发、知识空间、助手、文档和容量限制生效。
- 旧数据库、旧 Redis Key、旧对象目录和旧服务均不是启动依赖。

## 7. 非功能门禁

### 7.1 安全

- 跨租户、跨资源、跨行和字段遮蔽测试全部通过。
- 数据库、响应、日志、审计和测试产物不存在明文模型密钥。
- 出站地址覆盖 DNS 重绑定、重定向、环回、链路本地、云元数据和私网测试。
- 设备凭据固定范围、有效期、撤销、频率和并发限制有效。
- 没有未批准的高危或严重依赖、镜像和许可证问题。

### 7.2 RAG 质量

首周评测集至少包含：

- 门店事实问答、位置、价格、销量排序和无数据问题。
- 校园制度、图书馆服务、时效冲突、无权限和含糊问题。
- 每个场景包含允许、拒答、过期、冲突和越权样本。

发布阈值在 WP-0002 激活前由产品和测试签署，至少覆盖 Recall@10、事实依据、引用正确率、正确拒答率和越权暴露数。越权证据暴露容忍度为零。

### 7.3 性能

在固定数据量、并发、硬件、模型桩和真实模型烟测条件下分别报告：

- 鉴权与策略耗时。
- 结构化查询耗时。
- 混合检索与重排耗时。
- 流式首 Token 和完整回答耗时。
- 最大稳定并发、错误率和资源占用。
- 慢模型、向量存储抖动、队列积压和取消行为。

不得用模型桩结果宣称真实厂商端到端性能。

### 7.4 工程质量

- Maven Enforcer、依赖收敛、SBOM、SCA、许可证和容器扫描通过。
- Spring Modulith 与 ArchUnit 规则通过。
- 核心聚合、应用服务、接口、厂商和查询语言具备测试。
- 覆盖率只作为缺口信号，不替代关键行为断言。
- 构建可重复，镜像通过摘要固定，迁移可前向执行。

### 7.5 运维

- Compose 从空卷一次成功启动。
- 配置和密钥缺失时安全失败并给出可行动诊断。
- 存活、就绪、指标、日志、追踪和告警可用。
- 数据库、对象存储、向量索引和配置完成备份恢复演练。
- 发布、回滚、容量限制和数据清除有运行手册。

## 9. 测试分层

1. 无网络领域和应用单元测试。
2. 架构规则与模块验证。
3. 数据库、Redis、对象存储和向量存储集成测试。
4. WireMock 厂商协议与错误分类测试。
5. Spring AI 适配器契约测试。
6. HTTP、SSE、幂等、乐观锁和游标接口测试。
7. 权限、密钥、SSRF、上传和数据清除安全测试。
8. 固定黄金集 RAG 评测。
9. Docker Compose 端到端测试。
10. 可选真实厂商烟测与夜间兼容测试。
11. 性能、故障、备份、恢复和回滚演练。

真实厂商烟测必须使用独立低权限密钥和预算，失败不能被无网络测试掩盖。

## 10. 跨会话执行协议

每次会话开始：

```bash
git status --short --branch
make project-status
make resume-context
```

随后读取 `project/CHARTER.md`、`project/STATE.yaml`、当前工作包及其 ADR，确认 `lastVerifiedCommit` 与当前代码关系。

每次会话只推进一个主要工作包。新发现写入风险、决策或新工作包；没有 ADR 不改变公共契约、领域边界、权限、模型能力和数据结构。

每次会话结束：

- 执行工作包声明的验证。
- 登记测试、报告、截图、部署记录和提交。
- 更新工作包和 `STATE.yaml`。
- 记录未解决问题和下一前沿。
- 没有证据不能标记完成。

## 11. 发布阻断条件

以下任一条件失败即禁止合并或发布：

- 控制面与代码状态不一致。
- 工作包缺少验收证据或提交。
- 公共变化缺少 ADR。
- DDD 模块规则失败。
- 模型凭据可能泄漏。
- 出站地址未经过策略校验。
- 存在租户、资源、行或字段数据泄漏。
- RAG 评测未达到已签署阈值。
- Docker 部署、备份、恢复或回滚失败。
- 存在未批准的高危或严重漏洞。
- 页面入口没有角色、任务、结果和闭环。
- 新系统依赖旧系统才能启动。

阻断项只能通过修复并补充证据关闭，不能通过修改状态文件宣告消失。
