# ADR-0052：评测与发布制度的租户授权边界

## 状态

已接受（方案 A）。

## 日期

2026-08-05

## 决策负责人

产品、架构、安全、助手负责人和租户运营负责人。

## 背景和难以逆转的约束

ADR-0050 与 ADR-0051 已确定 evaluation-operations 拥有私有评测数据集、评测运行、无例外发布决定及
授权结果，但没有确定谁可登记合成数据集、触发运行和形成自动发布决定。

现有租户会话的权限集合已经包含 `assistant:write`，`AssistantService.publishVersion` 也以该权限保护助手版本
写入。代码图谱确认仓库没有 `evaluation:write` 或 `release:write`，也没有可把新权限安全授予既有成员的角色
管理、邀请或批量回填路径。直接引入一个无授予路径的新权限会使所有既有租户无法使用已经接受的评测制度；
自动把权限加给全部成员则会扩大最小权限边界。

评测正文仍是 evaluation-operations 的私有内容：即使具有写权限，也不获得下载、普通查询、审计投影、浏览器
缓存或日志中的题目、回答、候选及期望证据正文。

## 提案内容

推荐采用方案 A：在 M6 的无例外发布制度中，评测数据集登记、运行触发和基于运行的自动 `ReleaseDecision`
均要求同租户 `assistant:write`；实际 `AssistantVersion` 发布继续同时要求该权限和 evaluation-operations 返回的、
与目标草稿修订完全匹配的 `ReleaseAuthorization`。

1. `assistant:write` 是本切片唯一的用户授权条件。请求者、租户、成员、权限和追踪标识只能从
   `TrustedRequestContext` 恢复，不能由数据集、运行或发布请求参数提交。
2. 拥有该权限的成员可登记仅 `SYNTHETIC` 的私有数据集、触发其租户内草稿版本的评测并请求自动形成决定；
   不能读取、导出或修改已发布数据集正文，也不能替其他租户发起运行。
3. `ReleaseDecision` 不是人工批准。它只能由冻结 `EvaluationRun` 的通过或失败结论导出，且没有例外、批准人、
   理由正文或期限；`assistant:write` 不得绕过 `ReleaseAuthorization` 直接发布。
4. 当前不新增 `evaluation:read`、`evaluation:write`、`release:write`、平台全局权限、角色默认授予、成员邀请
   或权限回填。将来若需要职责分离，必须由新的 ADR 一并定义权限授予、撤销、历史迁移、会话失效和浏览器验收。
5. HTTP 或浏览器投影至多返回数据集／运行／决定的无正文标识、版本、计数、指标和结论。读取正文的任何新接口
   均不在本 ADR 授权范围内。

## 主要备选方案及拒绝原因

### 方案 A：复用 `assistant:write` 并保留冻结授权复核

推荐。它与既有助手版本写入语义一致，不创建无法授予的新权限，也不把自动评测结论降为页面布尔值。写权限只能
发起受控流程，最终发布仍受完全匹配的冻结运行和决定阻断；正文读取边界不随写权限扩大。

### 方案 B：立即新增 `evaluation:write` 与 `release:write`

拒绝。仓库当前不存在面向既有成员的角色治理、默认授予、撤销或会话失效链路。新增未授予权限会使已接受能力
不可达；静默批量授予又缺少最小权限、回滚和人工确认依据。

### 方案 C：只允许平台管理员管理所有租户评测

拒绝。它会把平台会话扩展为租户评测内容所有者，违背 ADR-0027 的显式范围和最小披露边界；平台权限不应成为
跨租户正文或版本控制的捷径。

## 后果和后续证据

接受后，先以红灯证明：无 `assistant:write`、伪造租户参数、跨租户数据集／运行或不匹配发布授权均失败；具有
权限的成员也只能得到无正文投影。随后再补私有内容端口、真实 PostgreSQL、自动配置、HTTP 和浏览器角色回归。

本 ADR 不授权独立评测角色、正文读取、人工例外、预算、审计导出、成员权限管理、M7 或 M8 实现。
