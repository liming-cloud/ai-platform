# ADR-0082：后端上下文与扩展的编译依赖边界

| 字段 | 值 |
| --- | --- |
| 编号 | ADR-0082 |
| 状态 | 已接受 |
| 日期 | 2026-09-23 |
| 任务 | GOV-0003 |

## 状态

已接受。依据用户明确要求执行《后端上下文依赖边界整改计划》；仅决定本次编译边界，不改变产品范围和里程碑结论。

## 背景

ADR-0022 确定了上下文拥有的四层结构，但当前 Maven 模块间虽无环，仍存在跨上下文直接导入 `domain`、内部 `application`、`infrastructure` 和自动配置类的情况。原架构守卫没有解析 Maven 依赖和 Java 导入，无法阻止此类回退。

## 决定

1. 上下文可通过 Maven 依赖其他上下文，但业务编译引用只进入被依赖上下文的 `application/.../facade`。公开输入、输出和值类型也置于该 facade；不能仅因类型是 `public` 就视为公开契约。
2. 扩展可依赖所属上下文的公开 `application/.../port/out` 及为该端口声明的 `application/.../facade` 契约。端口的请求、结果和枚举不得要求扩展直接导入上下文 `domain`。
3. 跨上下文和扩展均不得导入其他上下文的 `domain`、非 facade 的 `application`、`infrastructure` 或自动配置类。各上下文自行注册其自动配置，启动模块装配运行进程。条件装配需要排序时可使用 Spring 的 `afterName` 声明类名，不形成对他方基础设施的编译依赖；启动集成测试必须证明所需事实源实际就绪。
4. 每条上下文 Maven 编译依赖必须有对应的公开包使用并在治理任务中说明；禁止依赖环。架构守卫同时检查 POM 图和源码导入，不能用宽泛包前缀或历史基线豁免新增违规。
5. 迁移时在拥有者上下文内部将公开 DTO 转换为领域对象，保留业务校验、租户隔离和失败语义。此决定不改变 API、持久化结构或已经接受的业务范围。

## 后果

公开契约调整会触及现有适配器和测试替身，需运行受影响模块及完整后端验证。若端口签名泄露领域类型，应修改端口与调用方，不能将这些 `domain` 包登记为扩展合法例外。历史 ADR-0022 的决策时点事实不改写；现行依赖矩阵在 `docs/architecture/backend.md` 维护。
