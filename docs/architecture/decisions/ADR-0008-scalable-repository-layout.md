# ADR-0008：可扩展仓库与模块目录

## 状态

已接受

## 背景

ADR-0002 只确定了限界上下文、Maven 多模块和三个运行进程，没有回答公共契约、上下文内部目录、厂商扩展、前端多界面、数据库迁移、部署、跨系统验证和生成产物如何组织。目录过粗会让后续开发人员重新解释边界，最终形成新的 `common`、`utils`、巨型适配器和运行时耦合。

## 备选方案

### 方案一：每个限界上下文一个 Maven 模块

优点是模块数量可控，领域、应用和适配器的变更保持在同一所有权边界。缺点是领域层与 Spring 依赖处于同一编译类路径，需要架构测试强制依赖方向。

### 方案二：每个限界上下文按领域、应用、接口和适配器拆分 Maven 模块

优点是编译边界最强。缺点是七个上下文会快速产生二十多个基础模块，一个纵向行为需要跨多个 POM 修改，装配和测试成本超过六人团队当前收益。

## 决策

选择混合方案：

- 每个限界上下文默认是一个 Maven 模块，内部按 `api`、`domain`、`application`、`adapter` 分包。
- `api` 是唯一允许跨上下文使用的命名接口，Spring Modulith 和 ArchUnit 阻止内部包访问。
- 模型厂商、数据连接器、向量存储、对象存储、密钥存储、渠道和工具等独立变化点使用单独的编译期扩展模块。
- 三个 Spring Boot 运行入口只负责装配，不包含领域规则。
- 前端使用多应用工作区，控制台、问答和设备界面独立构建，共享包只有出现两个真实消费者时才创建。
- 外部 HTTP、事件、JSON Schema 和 Query DSL 契约统一放在根 `contracts/`。
- 单元和上下文集成测试靠近源码，跨运行时验收、安全、性能、评测和故障测试放在根 `verification/`。
- 详细目录、依赖矩阵、创建条件和 M1 最小落地范围由 `docs/architecture/foundation-repository-layout.md` 规定。

## 影响

- 新增模型厂商通常只新增一个扩展模块，并修改对应运行时依赖。
- 新增行业场景不创建新的核心上下文，通过数据集结构、助手和渠道配置表达。
- 禁止建立无所有者的 `common`、`shared`、`utils`、`manager` 或巨型基础设施目录。
- 目录树是边界契约，不要求提前创建没有源码和消费者的空目录。
- 如果某个上下文以后需要独立部署，再以调用、容量和所有权证据形成新 ADR，不提前拆成微服务。
