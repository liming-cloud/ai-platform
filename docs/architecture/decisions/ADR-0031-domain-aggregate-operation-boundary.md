# ADR-0031：领域聚合所有权与操作边界

## 状态

已接受

## 日期

2026-07-29

## 背景

领域层已经定义 `AggregateRoot`、`Entity` 和 `ValueObject`，但部分写入流没有将它们用作完整的操作边界：应用服务可分别创建或变更 `AssistantVersion`、`SyncArtifact`、质量结论和发布事实，持久化实现也承担了本应由领域决定的归属与一致性校验。原有领域设计主要描述产品对象，缺少一份覆盖后续研发与评审的全平台可执行规约。

这会造成两类风险：一是具有独立标识、独立读取和生命周期的对象没有成为聚合根；二是应用层能够绕开聚合，把聚合成员和值事实拼装为持久化写入。后续 M3 数据源类型和后续里程碑若沿用该方式，领域不变量会继续分散。

## 决策

### 全平台规约

`docs/architecture/foundation-domain-design.md` 第 14 节成为全平台领域设计规约，覆盖统一语言、上下文所有权、聚合、实体、值对象、读取投影、领域服务、仓储、命令、事件、租户安全、测试、人工评审和例外治理。所有未来工作包都必须先提供领域设计卡；本 ADR 只固定不可逆规则和首批整改分类。

### 聚合分类

- 可由外部标识独立读取、持久化、发布、退役或参与并发控制的可变领域对象必须实现 `AggregateRoot`。首批整改对象为 `AssistantVersion` 与 `SyncArtifact`，它们分别与 `Assistant`、`GovernedDataSource` 以标识关联，不是可被外层随意操作的成员实体。
- 只表达不可变业务事实的对象必须实现 `ValueObject`，不得实现 `Entity`。`SourceRevision`、质量结论和已发布产物快照属于此类；它们由相应聚合根创建、校验和冻结。
- 没有独立生命周期的读取投影不得伪装为 `Entity`。`MemberAuthenticationProfile` 改为不可变值投影。

### 操作边界

- 外部写入只能调用聚合根的方法，或调用显式领域服务。领域服务只处理跨聚合不变量，并产出不可变的领域操作结果；它不承担鉴权、HTTP、事务框架、外部 I/O 或持久化技术。
- 应用服务只负责身份与权限、幂等、加载聚合根、调用外部端口、调用聚合根／领域服务，以及提交领域操作结果。它不得直接创建、变更或持久化聚合成员实体，不得自行拼装质量、发布或版本生命周期事实。
- 值对象可以作为命令、查询和领域操作的不可变输入输出；但由聚合状态派生、会被持久化为生命周期事实的值对象，必须由对应聚合根或领域服务创建。
- 跨聚合一致性必须以命名的领域服务和操作结果表达。例如助手版本号分配、数据源同步完成和产物发布；应用层不得把多个根的状态变化散落在条件分支中。

### 持久化与门禁

- 仓储端口只接收／返回聚合根、不可变读取投影或领域操作结果；基础设施只执行映射、锁和原子提交，不补充业务归属、质量或状态机判断。
- 新增应用服务构造器不得注入 `Entity`、`AggregateRoot` 或普通 `ValueObject`。可复用、无状态的领域规则必须以专用 `DomainPolicy` 契约注入，不能伪装为普通值对象。
- 后端架构门禁必须检查：生产领域中不存在非聚合根 `Entity`；应用服务构造器不存在上述领域状态对象依赖；已有违规回归为零后不得再引入。

## 备选方案

### 方案 A：把所有关联对象都塞进一个父聚合

拒绝。`AssistantVersion` 和 `SyncArtifact` 有独立标识、查询、发布及并发语义。强行作为父根的内存成员会制造无限增长的聚合，也会让历史读取和事务边界失真。

### 方案 B：保留现有实体，并以代码评审约束应用层

拒绝。当前问题已证明仅靠约定不足以阻止应用层和基础设施补写领域规则；必须由类型分类、领域 API 和自动门禁共同约束。

## 后果

本 ADR 扩展 WP-0011 的实现前置条件：在继续 `OBJECT_STORAGE` 与 `STRUCTURED_DATASET` 之前，先完成助手版本、受治理数据源同步／发布和认证投影的分类整改，新增领域服务与操作结果，并以红绿门禁证明规则可执行。后续每一工作包均须使用第 14.6 节的领域设计卡，并在所在 M 阶段人工评审中复核。

该决策不改变已接受的租户隔离、数据源生命周期、发布快照、索引版本和模型治理语义；它只把这些语义收回到正确的领域入口。后续任何新增领域对象必须先按本 ADR 选择“聚合根、值对象、读取投影或显式领域服务”之一，不能以未归属实体落地。
