# ADR-0073：平台拥有租户管理员生命周期与人员身份互斥

## 状态

提议，等待人工接受。

## 日期

2026-08-31

## 决策负责人

用户，代表产品、架构、安全、平台运营与租户运营负责人。

## 背景和待消除的矛盾

ADR-0042 已把登录凭据收敛为唯一全局 `SubjectIdentity`，ADR-0047 已要求平台操作者在建立租户时
显式选择另一个活动主体作为初始管理员，ADR-0061 与 ADR-0067 又分别固定了全局账户所有权和三种
产品角色。当前实现仍存在三项与目标 SaaS 责任边界冲突的行为：

1. 租户成员候选只排除当前租户已有成员，活动 `PLATFORM_ADMINISTRATOR` 仍可被选中；成员建立命令也
   只复核主体活动状态和同租户唯一性。
2. 持有 `access:manage` 的租户管理员可以给成员绑定 `TENANT_ADMINISTRATOR`，也可以停用或撤销其他
   租户管理员，只由“最后一个访问管理员”规则兜底。
3. 平台角色绑定命令只检查目标账户和重复绑定，不检查目标是否已有启用的租户成员资格。候选过滤与
   前端隐藏因此都不能构成并发安全的权限边界。

ADR-0072 第 2 条允许同一人员同时拥有平台与租户身份，只要求显式切换会话。人工产品复核进一步要求
平台管理员不出现在租户成员候选中，并由平台独占租户管理员生命周期。两种语义不能同时作为最终事实，
必须由本 ADR 明确取舍；在本提议被接受前不得修改生产授权逻辑。

## 提议决策

选择方案 A：平台拥有租户管理员生命周期，租户管理员只治理普通成员；活动平台角色与启用租户成员
资格互斥。若本 ADR 被接受，第 3 条只在“同一主体可同时持有活动平台角色与启用租户成员资格”这一点
取代 ADR-0072 第 2 条，其余知识库所有权与双范围会话边界继续有效。

1. `organization-access` 继续拥有唯一 `SubjectIdentity`、平台角色绑定、租户成员资格和租户角色绑定。
   不复制账户，不增加第二套凭据，也不把授权规则下沉到控制器或 Mapper。
2. 只有 `PLATFORM_ADMINISTRATOR` 能建立、分配、替换、停用或恢复 `TENANT_ADMINISTRATOR`。新租户建立
   仍在一个事务中建立租户、初始管理员成员资格和固定管理员角色；完成页必须明确显示自动分配结果。
3. `TENANT_ADMINISTRATOR` 只能建立、启用、停用和授权当前租户的 `TENANT_USER`。租户命令若以管理员
   成员为目标，或尝试绑定、撤销 `TENANT_ADMINISTRATOR`，必须在服务端失败关闭；自身和同级管理员
   不因前端隐藏而获得例外。
4. 一个主体可以在多个租户拥有成员资格，角色按租户独立。主体可由平台分配为多个租户的管理员，
   也可在不同租户分别是管理员或普通用户；任何租户成员资格都不能产生平台能力。
5. 活动 `PLATFORM_ADMINISTRATOR` 绑定与任何启用的租户成员资格不能同时存在。已撤销的平台绑定与已
   停用的成员资格可作为审计历史共存，但重新绑定平台角色或重新启用成员时必须再次检查另一侧当前事实。
6. 平台角色绑定、租户建立、成员建立和成员启用都先锁定同一 `SubjectIdentity` 行，再检查对侧状态并
   提交。候选目录只负责减少无效选择，命令侧检查才是安全边界；并发请求必须由共同主体锁串行化。
7. 活动或准备中的租户必须至少有一个启用的 `TENANT_ADMINISTRATOR`。允许多个管理员；替换操作必须
   先原子确认新管理员满足资格并建立角色，再停用旧管理员，不能暴露零管理员中间状态。
8. 普通成员候选固定为：活动主体、不是当前租户成员、没有活动平台管理员绑定。租户管理员候选额外由
   平台范围接口提供，并遵守同一互斥规则。平台角色候选只包含没有启用租户成员资格的活动主体。
9. 租户普通成员的角色或状态改变后撤销该成员的当前租户会话；租户管理员的分配、替换、停用或恢复
   撤销该主体全部租户会话；全局账户或平台角色变化继续按 ADR-0061 撤销该主体全部平台和租户会话。
   会话撤销失败必须使同一事务回滚。
10. 上线迁移先只读检查“活动平台管理员绑定与启用租户成员资格并存”的主体。发现冲突时迁移失败并
    输出不含登录名、租户名或凭据的计数；由平台运营显式撤销一侧后重试，不按最近使用或名称自动选择。
11. HTTP 与 SPA 只返回可行动的业务提示，不暴露角色内部码、主体标识、租户内部标识、SQL、异常或
    会话标识。目录、候选和命令使用同一资格谓词，但不得用读取投影替代写入复核。

## 公共契约与分层边界

- 平台租户治理增加租户管理员目录、分配、替换、停用和恢复用例；接口只接收受控账户选择与必要的
  乐观版本，不接收权限码、租户正文或客户端声明的平台身份。
- 租户成员建立与状态接口只操作普通成员；租户角色接口不再接受管理员角色变更。服务端按目标当前
  角色判断，而不是相信页面来源或请求中的“普通成员”声明。
- `interfaces` 只解析请求和投影安全错误，`application` 负责可信上下文授权、锁顺序、跨聚合资格复核、
  事务与会话撤销编排，`domain` 拥有角色所有权、互斥、最后管理员和状态转换不变量，`infrastructure`
  实现主体锁、资格查询、原子提交与安全分页。
- `SubjectIdentity`、`PlatformRoleBinding`、`TenantMembership` 仍是独立聚合。跨聚合规则由
  `PersonnelScopeEligibility` 领域服务根据受锁事实判定，不引入跨聚合对象引用或巨型账户聚合。
- 本 ADR 不授权租户自定义角色、个人直接权限、平台读取租户知识库、跨租户正文共享、账户硬删除或
  生产环境自动修复冲突数据。

## 主要备选方案及拒绝原因

### 方案 A：平台拥有租户管理员，活动平台角色与启用成员资格互斥

提议接受。责任边界与人工复核一致，能够从服务端消除平台管理员进入租户内容面的路径；依托现有
`SubjectIdentity` 行锁即可序列化跨聚合转换，变更局部且可验证。

### 方案 B：允许同一主体同时拥有平台和租户角色，只依赖显式会话切换

不推荐。虽然沿用 ADR-0072 当前文字且迁移最少，但会保留平台账户出现在租户候选、权限聚合和人工误配
风险；所有入口都必须持续解释双重身份，不能满足本轮 SaaS 管理模型的产品判定。

### 方案 C：给账户增加不可变 `PLATFORM_OPERATOR`／`TENANT_PERSON` 类型

不推荐。账户用途转换会变成不可逆数据迁移，且与现有角色绑定和成员资格重复表达同一事实。当前只需
约束活动状态组合，不需要新增账户种类。

### 方案 D：租户管理员继续治理同级管理员，只保留最后管理员保护

拒绝。它把租户普通成员治理权限扩大为管理员所有权，无法防止同级提权、降权或停用，也与人工评审
明确要求相反。

## 后果与验证

- 接受后先用红绿 TDD 固定四条写路径的共同主体锁和双向互斥，再实现平台租户管理员生命周期；不得先
  仅修改候选 SQL 或前端隐藏操作。
- 真实 PostgreSQL 必须覆盖候选与命令谓词一致、并发平台绑定／成员启用只有一个成功、多个管理员、
  最后管理员、跨租户角色、会话撤销失败回滚和迁移冲突失败。
- HTTP 必须证明租户管理员不能建立、停用、提升、降级或撤销管理员，平台管理员可管理管理员但不能
  获取租户正文能力；伪造目标角色、跨租户标识和过期版本均失败关闭。
- Compose 与 Chrome 分别使用平台管理员、租户管理员和普通用户完成角色任务，并续证 1024×768、
  390×844、真实 200% 缩放、键盘导航和 `prefers-reduced-motion`。
- 本提议只有在用户明确接受并登记接受证据后才能进入生产代码、数据库迁移和公共 HTTP 契约实施。
