# ADR-0048：统一浏览器登录入口与角色化工作区

## 状态

已接受

## 日期

2026-08-03

## 决策负责人

产品、架构与安全负责人。

## 背景和难以逆转的约束

当前 `console-web` 的数据、模型和治理工作区分别渲染登录表单，`query-web` 也维护独立的内存
令牌。浏览器新开页签或进入另一个工作区时会重复要求登录，产品没有一个能够按角色呈现可用任务的
入口。`ControlPlaneClient` 的影响分析覆盖 42 个符号，不能在单个页面存放令牌来局部掩盖该问题。

ADR-0033 要求请求身份只能从服务端验证的令牌恢复；ADR-0041 与 ADR-0043 进一步要求平台会话和
租户会话使用不同的 Sa-Token login type，任一令牌不能被另一种上下文解析器接受。单一浏览器入口
不能因此把平台范围、租户、成员、权限或令牌重新做成前端可提交的业务参数，也不能让平台管理员
读取租户正文。

浏览器跨页签复用登录态需要共享同源持久化媒介。把 Bearer token 写入 `localStorage` 或
`sessionStorage` 会扩大 XSS 可提取面；只依赖内存则无法实现产品要求的跨页签连续性。若改用
cookie，会引入 CSRF、注销传播、过期清除和本地 HTTP 测试语义，必须先固定安全契约。

## 决策内容

选择方案 B：浏览器只有一个同源登录入口；服务端以一次身份验证按已验证的角色分别签发范围
不可互用的浏览器会话，并以最小能力清单驱动导航。

1. 浏览器登录只提交登录名、口令，以及建立租户会话时必需的 `tenantCode`。该编码只用于会话建立时
   选择已验证成员资格，不会出现在后续业务请求、`TrustedRequestContext`、`PlatformRequestContext`
   或前端缓存的身份状态中。平台授权仍完全由服务端的 `PlatformAccessGrant` 判定。
2. 服务端一次验证 `SubjectIdentity` 后，可分别签发租户和平台两个独立 session token。它们仅以不同
   的同源 `HttpOnly`、`Secure`、`SameSite=Lax`、根路径 cookie 返回；生产 cookie 使用 `__Host-`
   前缀且不设置 `Domain`。浏览器 JavaScript 不读取、保存、拼接或显示 token；测试环境的非 Secure
   cookie 只能由隔离测试配置显式开启。
3. 租户解析器只读取租户 cookie 对应的 login type，平台解析器只读取平台 cookie 对应的 login type。
   同一次登录可以同时持有两者，但两种上下文继续独立恢复，平台上下文不含租户、成员或目标资源。
4. `GET /api/v1/auth/browser-session` 返回不含 token、凭据、成员详情或正文的能力清单，只包含当前可
   用的工作区类别、显示角色和会话过期提示。前端据此隐藏无权导航；每个业务接口仍由服务端上下文
   和权限再次授权，不能把能力清单当作授权依据。
5. 显式注销必须在一个服务端操作中撤销该浏览器登录族的所有已签发范围会话，并清除两枚 cookie。
   过期、撤销或 401 响应同样清除对应 cookie；同源页面通过 `BroadcastChannel` 仅同步“会话已失效”
   信号，不传递 token 或身份详情。
6. 所有非安全方法必须校验同源 `Origin`／Fetch Metadata，并使用服务端签发、非身份用途的 CSRF
   防护值。跨站、缺失或不匹配的防护信息一律失败关闭。浏览器不再使用现有 Bearer 响应体 token；
   机器调用的 Bearer 契约在明确迁移期内保持不变，直到另一个已接受 ADR 决定其替代或下线。
7. 每个产品页只消费统一浏览器会话能力清单，不再自行渲染登录入口。租户管理员只看租户任务；只有
   有效平台治理授权的主体才看平台租户生命周期任务；平台运营不因导航或 cookie 得到正文读取能力。

## 主要备选方案及拒绝原因

### 方案 A：在 `localStorage` 保存一个共享 Bearer token，并用 `BroadcastChannel` 同步

拒绝。它虽能减少重复登录，但任意同源脚本注入都能直接提取长期 token；前端还要自行拼接
`Authorization`，扩大错误清除和跨应用兼容面，不能满足最小凭据暴露原则。

### 方案 B：同源 HttpOnly 的双范围浏览器会话与能力清单

接受。一次身份验证带来一致的用户入口和跨页签连续性；两类 token 仍由不同解析器使用，既不
把平台范围做成可选租户上下文，也不让前端持有凭据。能力清单只改善导航，不改变服务端授权事实。

### 方案 C：签发一个可同时解析平台和租户的通用 token

拒绝。它使范围成为每个 Controller 都要理解的可选分支，直接违背 ADR-0041 与 ADR-0043 的不同
login type 和失败关闭边界。

### 方案 D：保持每个工作区独立登录和内存会话

拒绝。它与“一个登录入口、按角色使用已授权功能、跨页签一致”的产品结果相矛盾，并持续制造
相互独立的退出和过期状态。

## 后果和后续证据

- 接受后，先写红灯证明 token 不进入浏览器存储、租户 cookie 不能解析平台上下文、平台 cookie
  不能解析租户上下文、伪造能力清单不影响授权、CSRF／跨站写入失败关闭，以及注销／过期在同源页签
  一致失效。
- 再补齐平台安全领域与会话适配、组织访问登录编排、真实 Redis／PostgreSQL、自动配置、HTTP cookie
  合同和浏览器任务。浏览器任务至少覆盖一次登录进入租户与平台许可工作区、租户管理员看不到并无法
  直达平台路由、平台运营无法读取租户正文，以及跨页签注销与过期。
- 需要在正式 HTTPS 部署和隔离测试环境分别验证 cookie 属性；不得在文档、截图、日志、测试夹具或
  版本库记录真实 token、口令或主密钥。
- 接受本 ADR 不授权成员资格列表、邀请、密码重置、平台授权委派、正文导出、评测、预算、发布审批
  或 M7／M8 实现。

### 本地研发 HTTPS 证据延期

2026-08-04，产品负责人确认本地研发阶段不安装 macOS System keychain 的临时 CA，避免将仅为
`localhost` 验收生成的信任根扩大为整机基础设施。该延期不改变 `Secure`、`HttpOnly`、`SameSite`
或生产 `__Host-` cookie 契约，也不允许以忽略证书错误、非安全 cookie 或 HTTP 浏览器结果替代
正式证据。

本地只保留 HTTPS 覆盖层配置、自动化部署检查和不携带凭据的连通性检查。真实浏览器 HTTPS cookie
属性、同源跨页签注销与自然过期必须在拥有正式证书基础设施的部署环境重新执行，并作为 M6 自动验收
和进入 M7 前不可替代的安全证据。
