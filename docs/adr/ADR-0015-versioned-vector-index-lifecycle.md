# ADR-0015：版本化向量索引生命周期

## 状态

已接受

## 日期

2026-07-27

## 决策负责人

产品负责人批准的 M1 计划，由后端负责人实施并以自动证据验收。

## 背景与难以逆转的约束

WP-0003 已能发布受治理文本，但索引尚不存在。索引一旦被助手和查询引用，
其来源快照、分块语义、嵌入部署和向量维度就不能原地改变。模型调用和对象读取
耗时不可控，也不能进入数据库事务。近似向量索引在筛选后可能返回不足结果，
因此租户安全和召回要求必须先于规模优化。

研究依据见 `docs/research/WP-0004-indexing-baseline.md`。

## 决策

1. `IndexVersion` 属于知识与数据源上下文，字段至少固定：
   - 租户和知识空间。
   - 已发布数据源快照摘要。
   - 分块策略编号。
   - 嵌入部署标识、修订和维度。
   - 距离度量。
   - 构建摘要、状态和修订号。
2. 状态固定为：
   `BUILDING -> READY -> ACTIVE -> SUPERSEDED`，
   或由 `BUILDING` 进入 `FAILED`。失败和已替代版本不能重新激活。
3. 创建索引版本时，在单一 PostgreSQL 事务中：
   - 只选择当前租户和知识空间内状态为 `PUBLISHED` 的数据源。
   - 冻结数据源标识、发布内容版本、对象引用、摘要和长度。
   - 按稳定顺序计算来源快照摘要和构建指纹。
   - 创建 `BUILDING` 索引版本与唯一构建任务。
   相同幂等键和指纹返回原版本，同键不同指纹失败。
4. 构建任务由 `ingestion-worker` 通过数据库任务表认领。
   使用 `FOR UPDATE SKIP LOCKED`、租约、尝试次数和下一执行时间，
   保证多实例不会同时处理同一任务。对象读取与嵌入调用在事务外执行。
5. 重试始终消费索引版本冻结的来源快照。分块和向量以索引版本与稳定分块标识
   唯一，完整产物与 `READY` 状态在同一事务提交；失败产物不能被活动查询读取。
6. 首个分块策略为 `paragraph-window-v1`：
   - UTF-8 文本先统一换行为 LF、移除开头 BOM、执行 Unicode NFC，
     并移除文档首尾空白行。
   - 空白行分隔段落，每个非空段落独立成块。
   - 超过 800 个 Unicode 码点的段落使用 800 码点窗口和 80 码点重叠，
     不拆分代理项。
   - 分块顺序从 0 开始；分块标识由来源摘要、策略、顺序和块摘要共同生成。
7. 模型目录与运行时上下文公开框架无关的 `EmbeddingModelPort`。
   输入包含不可变部署标识与修订、期望维度和按序文本；
   输出必须数量相等、顺序一致、维度一致且所有值有限。
   Spring AI `EmbeddingModel` 只存在于模型厂商扩展。
8. M1 使用固定的 128 维确定性嵌入部署，仅证明合同、权限、索引和检索闭环，
   不宣称代表真实模型语义质量。真实 OpenAI Compatible 与 Ollama 嵌入适配器
   仍必须通过相同平台合同。
9. pgvector 表使用不固定维度的 `vector` 列，并保存维度字段与检查约束。
   M1 使用精确余弦距离；查询必须同时约束租户、知识空间、`ACTIVE` 索引版本、
   嵌入部署、修订和维度。
10. 只有容量证据证明精确检索不达标时，才允许按嵌入部署、修订和维度创建部分
    HNSW 表达式索引。启用前必须重新验证 Recall@10、过滤后结果完整性、内存和构建时间。
11. 发布索引使用带预期修订号的单一事务：将原 `ACTIVE` 版本改为
    `SUPERSEDED`，再把目标 `READY` 版本改为 `ACTIVE`。任一步失败则整体回滚，
    旧活动版本继续可用。
12. 向量写入由独立 `vector-pgvector` 扩展实现。知识上下文只依赖公开写入端口；
    可信查询上下文只依赖公开候选检索端口。扩展不能进入领域模型。
13. 候选检索必须接收服务端 `TrustedRequestContext` 并检查 `knowledge:read`。
    无权限、不存在和跨租户对外不可区分。下一工作包在生成前再次执行证据授权。

## 主要备选方案及拒绝原因

### 直接修改单一活动向量集合

拒绝。模型、维度或分块变化会产生混合向量，查询结果无法追溯，也无法原子回滚。

### 创建索引时同步读取对象并调用模型

拒绝。长时间外部调用会占用请求和数据库事务，重试与超时也无法稳定恢复。

### M1 直接使用 HNSW

拒绝。数据规模尚无证据需要近似检索，而过滤后候选不足会削弱召回与租户内结果完整性。

### 为每个嵌入维度创建一张核心业务表

拒绝。模型维度变化会扩散到业务迁移和领域契约。无固定维度列加索引版本约束更局部。

### 使用 Spring AI VectorStore 作为领域契约

拒绝。它会把框架文档、过滤表达式和存储语义泄漏到知识与查询上下文，
也无法替代本项目的版本状态和原子激活规则。

## 后果与后续证据

- PostgreSQL 演示镜像切换为固定摘要的 pgvector 0.8.5 与 PostgreSQL 18。
- 知识数据迁移新增索引版本、来源快照、构建任务和分块向量表。
- 控制面负责创建与发布；摄取进程负责构建；查询进程在下一工作包消费活动版本。
- WP-0004 必须提供确定性分块、幂等重试、维度失败、租户反例、原子激活、
  门店与校园命中及精确检索延迟证据。
- 达到大规模数据前不得把近似检索结果当作安全或完整性证据。
