# ADR-0062：租户历史直接权限退役与显式角色迁移

## 状态

已接受。

## 日期

2026-08-11

## 决策负责人

用户，代表产品、架构、安全与租户运营负责人。

## 背景和难以逆转的约束

ADR-0057 已接受“角色绑定是租户权限唯一治理路径”，并拒绝把个人直接授权作为默认路径。但当前
`organization_access.membership_permission` 仍参与租户认证和“最后访问管理员”保护；演示种子也仍写入
该表。它不是可直接删除的死数据。

代码图谱与演示数据确认，历史集合不能安全自动映射：两个成员拥有同一组 11 项权限，其中包含当前
`TenantPublishedPermission` 未发布的 `model-tenant:write` 与 `model-personal:write`；另一个成员仅有
`model-platform:write`。按权限集合自动创建角色会编造业务职责，并可能把不适用于租户角色的权限带入
新 RBAC。直接删除又会静默撤销现有可用能力。

## 提议的决策内容

选择方案 A：**由租户运营负责人提供显式、可审计的历史权限迁移清单；只有经过完整性验证的成员资格
才能原子地转为角色绑定并删除直接权限。**

2026-08-11，用户代表产品、架构、安全与租户运营负责人接受方案 A。该接受只授权实现清单驱动、
逐成员失败关闭的迁移机制；它不把尚未提供的历史成员资格、目标角色或撤销例外视为已批准。尤其是
`model-tenant:write`、`model-personal:write` 与 `model-platform:write` 仍必须在实际清单中逐项映射到
已接受的职责，或逐项登记批准撤销，迁移器不得推断。

1. 迁移清单以 `tenantId`、`membershipId`、历史直接权限摘要和目标角色集合表达业务决定。目标只能引用
   当前租户的活动自定义角色或已发布的内置角色；它不接受前端、调用方或数据库自动推断的角色名称。
2. 执行前服务端对每项清单重读当前直接权限、成员状态和已有活动角色。若迁移后有效角色权限与迁移前
   有效权限不相等，必须由同一清单逐项列出经人工批准的撤销权限；未映射、过期、跨租户、停用成员、
   未发布权限或并发版本变化一律拒绝，不删除任何行。
3. 每个成员资格的迁移在同一事务中写入缺失角色绑定、推进 `permissionVersion`、撤销该成员全部租户
   会话并删除其直接权限。会话撤销失败、角色绑定冲突或删除数量不匹配时整体回滚。
4. 包含当前无租户角色归属的 `model-tenant:write`、`model-personal:write` 或 `model-platform:write` 的
   历史集合不得由迁移器猜测归属。运营负责人必须先选择：为真实后端任务建立并接受相应租户／平台角色
   契约，或在清单中明确批准撤销。该选择不能由本 ADR 的实现悄悄完成。
5. 迁移完成前，`membership_permission` 仅作为待清理历史兼容事实，不得接受新写入。只有全库直接权限
   行数为零、迁移审计和真实 PostgreSQL 回归均通过后，才可由后续独立切片移除认证读取和表结构。
6. 审计只记录清单标识、操作者、租户／成员标识、前后权限摘要、角色标识、批准的撤销项、结果与时间；
   不记录口令、token、正文或完整会话材料。

## 迁移流程与影响边界

1. 租户运营负责人先从只读迁移状态投影导出历史直接权限摘要，并为每个成员资格提交目标角色和经批准的
   撤销例外；迁移器不接受浏览器能力码、token、当前操作者或任意权限字符串。
2. 应用服务锁定同租户成员资格，重读直接权限、活动内置／自定义角色、成员修订和清单摘要。任一差异、
   跨租户引用、停用角色、未发布权限或未批准的集合差异都失败关闭。
3. 单成员事务只在校验成功后写入缺失绑定、推进成员权限修订、调用
   `TenantMemberSessionRevoker`、写入最小审计事实并删除对应直接权限。撤销端口或数据库写入失败必须回滚。
4. 认证读取、成员停用与角色撤销中的直接权限分支暂时保留，直到迁移状态证明全库零行。届时以独立切片
   删除 `TenantMembershipMapper.findPermissionCodes`、四类“最后访问管理员”查询中的直接权限 `EXISTS`、
   演示种子和表结构；不得在本 ADR 接受后直接删除。

变化局限于 `organization-access` 的迁移应用服务、角色／成员存储、审计投影和控制台迁移状态；
`platform-security` 仅复用既有 `TenantMemberSessionRevoker`。不改变浏览器会话、导航投影、模型运行时、
厂商连接或任何业务接口的最终授权点。

## 主要备选方案及拒绝原因

### 方案 A：显式迁移清单与逐成员原子切换

提议接受。它保留运营方对职责语义的控制，同时用角色投影等价校验防止静默扩权或收权；失败成员保持
原有授权，不会把部分迁移误报为完成。

### 方案 B：按相同权限集合自动创建自定义角色

拒绝。权限集合不等于职责名称，且现有集合含未发布或范围不明的模型配置权限。自动生成角色会把历史
实现细节伪装成企业职责，并可能在不同租户中制造无法解释的角色目录。

### 方案 C：一次性删除全部直接权限，再由管理员手动重新授权

拒绝。它会在没有逐项批准的情况下撤销正在使用的能力，与 ADR-0057 的可解释和失败关闭要求冲突。

### 方案 D：永久保留直接权限作为与角色并行的授权来源

拒绝。认证、最后管理员保护和角色页面会持续面对两套权限事实，无法完成 ADR-0057 的 RBAC 闭环。

## 后果和后续证据

- 人工接受后，先以纯领域／应用红灯证明：缺失映射、集合不等、未批准撤销、跨租户、停用成员与旧版本
  均不会删除直接权限或撤销会话。
- 随后补齐真实 PostgreSQL 原子回滚、Sa-Token 会话撤销、受限 HTTP、迁移审计、服务端分页迁移状态和
  统一控制台受控任务；正式浏览器角色回归仍遵守 ADR-0048 的受信任 TLS 前置条件。
- 认证读取和 `membership_permission` 表删除必须另立后续切片，并以全库零行、完整迁移审计和全后端回归
  作为前置条件；本提议本身不授权删除任何权限。
- 接受本 ADR 不授权个人直接授权、平台自定义角色、服务账户、外部身份联邦、M7 或 M8。
