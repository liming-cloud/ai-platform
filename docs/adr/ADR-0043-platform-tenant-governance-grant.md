# ADR-0043：平台租户治理授权与启动边界

## 状态

已接受

## 日期

2026-08-03

## 决策负责人

用户，代表产品、架构与安全负责人。

## 背景和难以逆转的约束

ADR-0041 已要求 `PlatformRequestContext` 仅由已验证的平台 Bearer 会话恢复，且平台运营或
租户管理员不能取得平台治理范围。ADR-0042 已将密码摘要收回全局 `SubjectIdentity`，但没有
定义“哪些主体可建立、激活、挂起或恢复租户”的独立平台授权事实。

现有 `model-platform:write` 只表达平台模型配置治理。把它当作租户生命周期权限会把不相关的
模型职责隐式升级为平台租户管理，且无法证明平台会话、租户会话和内容读取边界。因此不能复用它，
也不能从租户成员资格、Header、请求参数或前端状态推导平台范围。

## 决策内容

接受方案 A：organization-access 保存独立的全局 `PlatformAccessGrant` 最小授权事实；只有
同时满足“已启用 `SubjectIdentity`”和“当前有效 `tenant-governance:write` 授权”的主体才能完成
平台登录并由 platform-security 签发 `PlatformRequestContext`。该上下文只含主体、凭据类型、渠道、
权限修订、权限集合和服务端追踪标识，不含租户、成员、目标资源或调用方追踪标识。

首条切片不提供平台授权管理接口。生产初始授权必须在受控部署／数据库变更流程中显式创建并留存
审计责任；演示环境只为既有 `platform-admin` 主体写入该最小授权。后续授权委派、邀请、密码重置、
外部联邦和平台运营角色管理需要新的 ADR。

平台管理路由收到 `PlatformRequestContext` 后，才可把显式路径中的 `tenantId` 作为生命周期业务资源
目标；该目标永远不是登录状态，也不授予知识、问答、对象或审计正文读取权限。

## 主要备选方案及拒绝原因

### 方案 A：独立 `PlatformAccessGrant` 与 `tenant-governance:write`

接受。授权事实、全局主体凭据和租户成员资格分属明确模型；平台会话的签发条件和租户治理权限
可单独撤销、修订与审计。平台上下文不会伪装为可空租户上下文。

### 方案 B：复用 `model-platform:write`

拒绝。模型配置管理与租户建立／挂起是不同业务职责；复用会让既有模型管理员静默获得跨租户治理权。

### 方案 C：由任意租户管理员或请求参数切换为平台范围

拒绝。它违反 ADR-0033 和 ADR-0041 的令牌派生范围；租户成员资格不应成为平台治理授权的替代品。

## 后果和后续证据

- 接受后先写红灯：租户令牌、只有 `model-platform:write` 的令牌、停用主体和伪造 Header 都不能解析平台上下文。
- 平台与租户会话必须使用不同的 Sa-Token login type；一种令牌不能被另一种解析器接受。
- 真实 PostgreSQL 必须证明主体禁用或平台授权撤销后不能签发新平台会话，且平台授权表不包含租户正文、成员凭据或密钥。
- 租户建立、激活、挂起和恢复仍仅使用 `tenant-governance:write`；平台上下文不成为通用跨租户内容读取入口。
