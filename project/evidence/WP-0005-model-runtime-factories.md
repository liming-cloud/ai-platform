# WP-0005：多供应商模型运行时证据

## 结论

平台已经建立框架无关的对话与嵌入调用契约，并通过独立扩展接入确定性替身、
开放兼容协议和 Ollama。运行时只从当前租户的已发布部署与冻结供应商修订构造，
按租户、供应商修订、部署修订和模型类型缓存，失败对象不进入缓存。

实现提交：`3c8cb1a52`

## 已证明行为

- 公共对话、流式分片、嵌入、用量和工厂契约不包含 Spring AI 类型。
- Spring AI 类型只存在于供应商扩展和控制面组合根，领域层仍只依赖允许的公共值类型。
- 对话与嵌入按模型类型使用独立工厂，不存在同时承载全部能力的巨型供应商适配器。
- 开放兼容协议和 Ollama 均提供对话、嵌入与最小模型调用探测。
- 模型部署探测会传递显式能力；嵌入部署不再错误地执行对话探测。
- 运行时只接受已发布部署，并核验租户、部署类型、供应商验证状态和冻结修订。
- 缓存键包含租户、供应商连接、供应商修订、模型部署、部署修订和模型类型。
- 缓存具备容量上限、空闲超时、按供应商或部署定向淘汰，并且不缓存构造失败。
- 运行时构造时才解析密钥；数据库、缓存键、普通日志和异常不包含密钥明文。
- 环境密钥适配器只接受受限变量名，保存后仍只暴露密钥引用。
- 所有网络模型在构造和探测前都执行出站地址策略；内部 Ollama 地址必须由运维精确批准。
- 控制面完整应用上下文已实际装配 `ModelRuntimeResolver`，并非只有模块级编译通过。
- 演示环境继续使用确定性替身，真实厂商调用不会在未显式配置时发生。

## 红绿证据

先建立运行时缓存与解析器用例，首次编译因实现缺失而失败；最小实现完成后，
7 项缓存和解析行为通过。随后增加 Spring AI 适配器、确定性、开放兼容协议和
Ollama 合同，架构测试首次发现供应商扩展依赖领域内部 `ModelType`，将其提升为
公共契约后模块边界恢复通过。

```bash
make validate
make deploy-up
make deploy-smoke
make acceptance-model-provider
make acceptance-model-deployment
make acceptance-index-search
git diff --check
```

结果：

- 后端 58 份测试报告、159 项测试通过，失败 0、错误 0、跳过 0。
- 项目治理 7 项、前端 14 项、前端类型检查、代码规范检查和两个生产构建通过。
- 两个演示场景和 8 个检索用例的数据门禁通过。
- 五个应用镜像重新构建成功，八个组合服务均处于健康状态。
- 供应商连接容器验收覆盖创建、探测、列表和密钥脱敏。
- 模型部署容器验收覆盖冻结修订、探测、发布和租户隔离。
- 门店与校园索引验收覆盖知识发布、候选命中和跨租户隔离。
- 代码图已探索嵌入端口、确定性适配器、供应商探测和仓储装配；对
  `EmbeddingModelPort`、`ProviderProbeRequest` 与 `ModelType` 执行影响检查，
  据此收敛公共契约及模块依赖方向。
