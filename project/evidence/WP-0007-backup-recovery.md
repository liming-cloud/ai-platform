# WP-0007 备份与隔离恢复证据

## 结论

在提交 `9656d70e732b75472710a1c3e28a2a9ae0bf7fd7` 上完成 PostgreSQL 与
MinIO 的一致业务备份，并恢复到独立项目名、独立网络、独立卷和独立端口的环境。
恢复后的两个租户、三个对象、模型部署、助手版本、查询用量和脱敏审计事实均可读取，
对象内容摘要与元数据一致，租户目录互不相交。Redis 按 ADR-0020 不恢复历史会话，
应用启动前键数为零，两个演示管理员均能重新登录。

本切片仅证明本机 Docker 演示环境的恢复能力，不代表生产级高可用、跨区域灾备或
真实厂商模型容量。

## 恢复边界

| 分类 | 内容 | 处理 |
| --- | --- | --- |
| 业务事实 | PostgreSQL 数据库 | 逻辑备份、摘要校验、隔离恢复 |
| 知识正文 | MinIO 对象及元数据 | 对象清单、逐对象摘要、隔离恢复 |
| 临时状态 | Redis 会话与缓存 | 不恢复，以空实例启动并重新登录 |
| 可重建状态 | 容器文件系统、缓存和暂存文件 | 由镜像、迁移和初始化流程重建 |
| 秘密 | 登录密码、令牌、密钥引用值 | 不进入可提交报告；完整备份为临时机密产物并已删除 |

## 实际演练

执行入口：

```bash
make recovery-demo
```

最终结果：

- 备份耗时 4 秒，恢复阶段耗时 18 秒。
- 演示恢复点目标为 24 小时，恢复时间目标为 3600 秒，本次达到目标。
- 恢复 2 个租户和 3 个被引用对象。
- 数据库事实摘要一致，对象字节摘要和元数据一致。
- Redis 恢复键数为 0，恢复环境启动后可以重新认证。
- 门店与校园的助手目录互不相交，跨租户访问未产生数据泄漏。
- 原演示环境演练前后保持健康，隔离恢复环境的 8 个服务全部健康。
- 演练结束后隔离容器、网络和卷均已删除，原环境 8 个服务保持健康。

机器可读报告：
`project/evidence/artifacts/WP-0007-recovery-drill.json`

租户标识或知识正文。报告契约由

`c0f2906352e82905bae999cba7369928dc24d8c5`。

## 失败关闭证据

前两轮演练分别暴露 MinIO 极简镜像缺少 `awk` 和 `grep` 的可移植性问题。两次失败
均返回非零状态，并由清理陷阱删除隔离资源；原演示环境继续健康。修复后增加回归测试，
不再依赖这两个容器内工具：

- `8b625db2a`：移除校验和解析对 `awk` 的依赖。
- `9656d70e7`：移除恢复校验对 `grep` 的依赖，并隔离客户端进度输出。

这两次失败不是通过忽略错误绕过，而是修复脚本后重新执行完整恢复。
