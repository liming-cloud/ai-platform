## 方案比较

已比较：

1. 每个限界上下文一个 Maven 模块。
2. 每个上下文按领域、应用、接口和适配器机械拆分多个 Maven 模块。

最终采用混合方案：

- 限界上下文默认一个模块。
- 上下文内部使用 `api`、`domain`、`application`、`adapter` 分包。
- 高变化外部依赖使用独立扩展模块。
- 三个可部署进程使用独立运行模块。
- Spring Modulith 与 ArchUnit 强制上下文和分层边界。

该方案避免粗粒度巨型基础设施模块，也避免六人团队维护二十多个基础分层模块。

## 代码图谱边界

代码图谱查询确认当前绿地设计分支没有可用于目录推导的产品源码或运行入口。目录设计因此以已接受的领域、产品、运行时和扩展决策为依据，不重新引入已删除旧系统结构。

## 人工评审重点

- 一个新模型厂商是否只需新增扩展模块和运行时依赖。
- 一个新行业场景是否能够通过数据集、助手、评测和渠道配置表达。
- 三个运行入口是否只装配所需能力。
- 前端三个应用是否具有清晰共享门槛。
- 数据库、Redis、对象存储、向量索引和事件是否有唯一负责人。
- M1 最小目录是否足以支撑一周演示，又没有创建空模块。
