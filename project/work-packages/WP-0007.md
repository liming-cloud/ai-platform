## 问题

M1 已经证明租户、数据、模型、助手、可信查询、配额、用量和审计的纵向闭环，
但“容器可以运行”尚不能证明演示站点可重复交付。当前缺少统一运行手册、数据保护
边界、隔离恢复演练、端到端容量基线、故障处理步骤和最终演示验收记录。

如果没有这些事实，新的执行者无法可靠部署或恢复环境；错误的清理、备份或恢复命令
还可能破坏现有演示数据。M1 退出前必须把可部署性提升为可复现、可恢复、可解释的
工程能力。

## 范围内

- 编写从空 Docker 环境启动、初始化、验收、停止和升级的运行手册。
- 固定 PostgreSQL、MinIO、Redis 和容器配置的状态分类与备份边界。
- 使用独立项目名、独立卷和隔离端口执行备份恢复演练，不覆盖当前演示环境。
- 验证租户、知识对象、活动索引、模型部署、助手版本、查询用量和脱敏审计事实。
- 明确 Redis 会话和可重建派生数据的恢复策略，不把缓存误当业务事实。
- 建立密钥、环境变量、对象存储目录、镜像摘要和日志脱敏检查。
- 建立确定性本地模型下的并发可信查询与关键接口容量基线。
- 演练数据库、对象存储、查询运行时和工作进程的停止、重启与健康恢复。
- 固化门店和校园两条演示脚本、演示限制、失败处理和环境清理说明。
- 生成 M1 最终验收清单，逐项绑定命令、提交、镜像和可复核证据。

## 范围外

- Kubernetes、服务网格、云厂商托管编排和多区域部署。
- 生产级高可用、自动故障转移、跨区域灾备和零数据丢失承诺。
- 外部密钥库、企业监控平台、日志平台和告警通知集成。
- 互联网域名、正式证书、网络防火墙变更和公开站点发布。
- 商业容量承诺、真实大模型吞吐结论和生产成本测算。
- M2 领域功能、公共接口或数据库模型扩张。

## 公共接口与数据

本工作包默认不新增公共业务 API，不修改领域模型和现有数据库结构。

预期新增或完善：

- `docs/runbooks/` 下的部署、备份恢复、故障处理和演示运行手册。
- `scripts/operations/` 下失败关闭、参数显式且保护当前环境的运维脚本。
- `project/evidence/artifacts/` 下不含秘密和业务正文的机器可读验收报告。
- Docker Compose 的非秘密运行配置、健康检查和资源限制。

如果实现中发现必须修改公共契约、持久化结构、数据保护策略或恢复语义，必须先形成
新的 ADR，并更新追踪矩阵后再实现。

## 约束

- 任何删除卷、覆盖数据库或对象目录的动作必须使用显式隔离目标，不能操作当前环境。
- 完整备份按机密运行产物保护且不得提交；可提交清单和证据不得包含模型密钥、
  登录密码、会话令牌、密码摘要、密钥引用或未脱敏业务正文。
- 恢复演练的目标为演示级恢复点不超过 24 小时、恢复时间不超过 60 分钟。
- 所有镜像必须按不可变摘要登记；禁止只记录可变标签。
- 运行手册中的命令必须由自动化或实际演练执行，不能只做文档推演。
- 容量结论必须记录硬件、数据规模、并发、预热、采样、分位值和错误率。
- 确定性本地模型的容量结果不得外推为真实厂商模型性能。
- 运维脚本必须支持安全重试、失败关闭和非零退出码，避免依赖交互式输入。
- 不以关闭既有风险项为本工作包前置条件，但必须在最终验收中明确剩余风险。

## 验收标准

- 新执行者只读取运行手册即可从空环境启动八个服务并通过五个应用入口检查。
- 能够生成不含秘密的 PostgreSQL 与 MinIO 备份清单和校验摘要。
- 能在隔离环境恢复备份，并验证关键业务事实、对象内容摘要和租户隔离。
- 恢复点与恢复时间达到本工作包目标，原演示环境在演练前后保持健康。
- PostgreSQL、MinIO、查询运行时和工作进程重启后可恢复服务，错误有明确处置步骤。
- 固定并发与数据规模下的查询容量测试达到已声明门禁，错误率为零。
- 门店与校园演示脚本分别完成登录、数据、模型、助手、查询、引用、治理和登出闭环。
- 最终证据包含 Git 提交、镜像摘要、命令结果、容量报告、恢复报告和剩余风险。
- `make validate`、项目治理、容器健康、固定评测和差异检查全部通过。
- M1 退出清单由产品、测试和运维职责共同确认后，才允许进入 M2。
